Architects Lab · Multi-Agent Systems Project

Building a Data Scientist Agent with CrewAI

Notes from a two-part project: first, the full ML regression workflow built manually (pandas, imputation, EDA, encoding, linear/random forest/XGBoost models, feature importance) — then the exact same workflow rebuilt as a crew of three autonomous AI agents that write and execute their own Python code. Structured for a Senior Engineering Manager weighing multi-agent orchestration frameworks against the code-first (LangChain, OpenAI Agents SDK) and low-code (n8n) approaches already studied.
Framing Why Build It Manually Before Automating It
▸

Goal: predict weekly units_sold for a supplement company from features like date, product, category, price, discount, and location. The project is deliberately split into two halves — first build the entire regression workflow by hand (load → clean → explore → encode → split → train → evaluate), then rebuild the identical workflow as a CrewAI multi-agent system that plans, writes, and executes its own code.

The stated reason for going manual first: if you don't understand every step of the workflow, you can't write a good task description for an agent to execute it, and you won't be able to judge whether the agent's output is actually correct.

Architect's Lens

This "understand it by hand before you delegate it to AI" sequencing is worth treating as a general engineering-management principle, not just a teaching device — the same logic applies to any Optimus tooling decision: don't let a squad automate a workflow with an agent until someone on the team has actually done it manually enough times to write a precise specification and recognize a wrong answer. Agent output that "looks plausible" is a real risk category when nobody on the reviewing side has ground-truth intuition for what correct looks like.

Active Recall: Why does the instructor insist on building the ML workflow manually before automating it with CrewAI? tap to reveal
Because writing precise task descriptions for an AI agent requires understanding every step of the workflow yourself, and being able to judge whether the agent's generated output and results are actually correct requires the same ground-truth understanding — without it, you can't write a good specification or catch when the agent gets something wrong.

Cleaning Handling Missing Values — Choosing the Right Strategy
▸
StrategyWhen to useTrade-off
Drop rowsVery few missing values, or a column is mostly emptySimple but wastes data — risky if missingness is widespread
Mean imputationNumeric columns, roughly normal distributionSensitive to outliers — a few extreme values skew the mean
Median imputationNumeric columns with outliers/skewMore robust than mean — unaffected by extreme values
Mode imputationCategorical columnsReplace with the most frequent category

from sklearn.impute import SimpleImputer
imputer = SimpleImputer(strategy='median')
df[cols_with_missing] = imputer.fit_transform(df[cols_with_missing])

Architect's Lens

The project explicitly notes a subtlety worth internalizing: the textbook-correct order is to split data into train/test FIRST, then impute — computing the median only from the training set and applying it to both, to avoid "data leakage" (information from the test set silently influencing preprocessing). This project deliberately imputes before splitting for simplicity, but flags this as a shortcut, not a best practice. Worth treating as a real checklist item for any production ML pipeline: is preprocessing fit only on the training data, or does it silently leak test-set information?

Active Recall: What is "data leakage" in the context of imputation, and why does splitting before imputing prevent it? tap to reveal
Data leakage happens when information from the test set influences how the model or preprocessing is built — e.g. if you compute the median for imputation using the FULL dataset (including test rows) before splitting, the imputed training values are subtly informed by test-set data the model should never have seen, making the evaluation less honest. Splitting first and fitting the imputer only on the training set avoids this, since the test set stays completely untouched until final evaluation.
Exploration EDA — Reading the Data's Story Before Modeling It
▸

Three visualization libraries compared: Matplotlib (the low-level "grandfather," static/interactive), Seaborn (built on Matplotlib, higher-level, better default aesthetics — "Matplotlib on steroids"), and Plotly (interactive, zoomable charts with 40+ chart types).

EDA steps followed: target variable distribution (histogram — checking for skewness, here a high value of ~2.05, flagged as a risk for linear models specifically), numeric feature distributions (histogram + box plot per feature, to spot outliers), categorical feature frequency (count plots), pairwise relationships (scatter plots against the target), and a full correlation heatmap across all numeric features.

Architect's Lens

The skewness check is the detail worth flagging as more than a passing observation — it directly foreshadows and explains the later result (linear regression underperforming at R²=0.67 while tree-based models like Random Forest reached ~0.80). Linear models assume roughly linear, symmetric relationships; a highly skewed target is a leading indicator that a linear model will struggle before you've even trained it. Reading EDA output as a prediction of which model family will work, not just a description of the data, is the more sophisticated way to use exploratory analysis.

Active Recall: What did the high skewness (~2.05) observed in the target variable's histogram predict about the later linear regression model's performance? tap to reveal
It predicted the linear regression model would underperform — and it did, achieving only R²=0.67 compared to ~0.80 for tree-based models like Random Forest. Linear regression assumes relationships close to linear/symmetric, so a highly skewed target distribution is an early warning sign that a linear model won't capture the data's structure well, visible before any model is even trained.
Preprocessing One-Hot Encoding — And the Multicollinearity Trap
▸ 
BAD:  red=1, yellow=2, green=3
      (implies green > yellow > red numerically — false ordering!)

GOOD (one-hot): red=[1,0,0]  yellow=[0,1,0]  green=[0,0,1]
      (each category gets its own binary column, no false ranking)

pd.get_dummies(df, columns=['category','location','platform'],
                drop_first=True)

Why drop_first=True matters: with 3 categories (e.g. Canada/UK/US) and no dropping, you get 3 binary columns — but if you know 2 of them, the 3rd is fully determined (perfectly predictable from the other two), creating multicollinearity — redundant, perfectly correlated predictor columns that undermine a linear model's statistical validity. Dropping one category (it becomes the implicit "baseline") removes the redundancy without losing information.

Active Recall: With 3 categories one-hot encoded and drop_first=True applied, how many columns are created, and why doesn't this lose information? tap to reveal
Only 2 columns are created (not 3). No information is lost because the 3rd category becomes the implicit "baseline" — if both remaining columns are 0, that row belongs to the dropped category by elimination. This avoids multicollinearity (perfect redundancy between columns) while still fully distinguishing all 3 original categories.
Evaluation Regression Metrics — What Each Number Actually Tells You
▸
MetricMeaningUnits
MAE (Mean Absolute Error)Average absolute prediction errorSame as target (e.g. units)
MSE (Mean Squared Error)Squares errors before averaging — penalizes large errors more heavilySquared units (hard to interpret directly)
RMSE (Root MSE)Square root of MSE — the "best" of the error metrics for interpretabilitySame as target — lower is better
R² (coefficient of determination)Proportion of target variance explained by the model, 0 to 1Unitless — closer to 1 is better

Rule of thumb applied in this project: R² > 0.9 = excellent, R² > 0.7 = good fit, below that = likely underfitting, consider non-linear models. Linear regression's R²=0.67 triggered exactly this conclusion, motivating the shift to Random Forest and XGBoost.

Active Recall: Why is RMSE generally preferred over raw MSE for communicating model error to a non-technical stakeholder? tap to reveal
Because MSE is in squared units of the target (e.g. squared units sold), which is hard to interpret intuitively — a large number that doesn't map cleanly to a real-world quantity. RMSE takes the square root of MSE, bringing it back into the SAME units as the original target variable, so "RMSE = 319" directly means "the model's typical prediction error is about 319 units sold" — immediately interpretable.

Each model followed the same three-step pattern: instantiate → .fit(X_train, y_train) → .predict(X_test), then compare predictions against y_test (ground truth) using the metrics above. XGBoost's hyperparameters (n_estimators, learning_rate, max_depth) were shown to matter significantly — running with default values instead of the tuned ones visibly degraded performance, a live demonstration that "just use XGBoost" isn't a free lunch without tuning.

Architect's Lens

The near-identical final performance between Random Forest and tuned XGBoost (0.80 vs 0.81) is itself a useful data point: more sophisticated algorithms don't always translate into meaningfully better results on a given dataset — the actual gain here came from moving off linear models entirely (0.67→0.80), not from XGBoost's fancier gradient-boosting mechanics over Random Forest's simpler bagging approach. Worth remembering as a prioritization heuristic: the biggest performance jump usually comes from picking the right MODEL FAMILY for your data's shape, not from endlessly tuning within one family.

Active Recall: Which model transition produced the larger performance jump — linear regression to Random Forest, or Random Forest to tuned XGBoost? tap to reveal
Linear regression to Random Forest produced the larger jump (R² 0.67 → ~0.80). The jump from Random Forest to tuned XGBoost was much smaller (~0.80 → ~0.81) — illustrating that switching model FAMILIES (linear to tree-based) mattered far more here than further sophistication within the tree-based family.

Framing Why CrewAI — Multi-Agent Orchestration as "an AI Company"
▸

CrewAI is an open-source Python framework for building teams of coordinated AI agents — the explicit analogy used throughout is a company's departments (sales, engineering, marketing) working together toward a shared business goal, rather than one monolithic agent doing everything.

ComponentRole
Agentrole + goal + backstory (persona) + LLM ("brain") + optional tools + delegation on/off
ToolA capability an agent can invoke — web search, file I/O, code execution, custom APIs
Taskdescription + expected_output ("definition of done") + assigned agent + optional context (prior tasks' outputs feeding in)
Crewagents + tasks + process (sequential or hierarchical)

Sequential process: tasks run one after another, each output feeding the next via context — simple and predictable (used throughout this project). Hierarchical: a manager agent dynamically delegates to subordinates — more powerful, more complex, not used here.

Architect's Lens

Comparing this directly to the n8n notes and the OpenAI Agents SDK/MCP notes from earlier: CrewAI sits conceptually between them — more structured and role-oriented than a single flat agent with many tools (OpenAI Agents SDK), but more code-native and version-controllable than n8n's visual canvas. The "role + goal + backstory" persona pattern is a genuinely distinct design choice worth noting — giving each agent an explicit narrative identity (not just a system prompt) appears to meaningfully shape how reliably it stays in its lane during a multi-agent handoff, which is exactly the kind of role-discipline problem that gets harder as agent count grows in any Optimus-style multi-agent tooling.

Active Recall: What's the practical difference between CrewAI's "sequential" and "hierarchical" process types? tap to reveal
Sequential: tasks execute one after another in a fixed, predetermined order, with each task's output feeding into the next as context — simple and predictable. Hierarchical: a manager agent dynamically decides how to delegate tasks among subordinate agents at runtime — more flexible and powerful, but also more complex to reason about and debug.
Design The Three-Agent Data Science Team
▸ 
1. Planner Agent
   - Role: Lead Data Scientist and Planner
   - No tools — generates a numbered plan only, doesn't execute code
   - Output: sequenced instructions for the other two agents

2. Analyst/Preprocessor Agent
   - Tools: notebook_code_executor
   - Inspects data, imputes, encodes, splits into train/test —
     ALL via generated-and-executed Python code, not the agent
     "reasoning" about the answer

3. Modeler/Evaluator Agent
   - Tools: notebook_code_executor
   - Trains model(s), evaluates metrics, extracts feature
     importance — again via generated-and-executed code

Critical design principle repeated throughout: these agents don't calculate anything themselves in the LLM sense — they write Python code that performs the calculation, then execute that code via a custom tool. This is a deliberate and important distinction: an LLM "eyeballing" a mean squared error would be unreliable; an LLM writing correct mean_squared_error(y_test, y_pred) code and running it gets an exact, deterministic answer.

Architect's Lens

This "agent writes code, then executes it, rather than reasoning numerically itself" pattern is the single most important architectural decision in the whole project, and it's a general principle worth applying anywhere precision matters: LLMs are unreliable at arithmetic and exact computation done "in their head," but highly reliable at writing correct code that a deterministic interpreter then executes exactly. Any agentic system doing quantitative work (financial calculations, metrics, anything audit-sensitive) should follow this same "generate code, don't generate the number directly" discipline.

Active Recall: Why do the analyst and modeler agents generate and execute Python code rather than computing results directly through LLM reasoning? tap to reveal
Because LLMs are unreliable at precise numerical computation done purely "in their head" through text reasoning, but highly reliable at writing syntactically correct code that a deterministic Python interpreter then executes exactly — offloading the actual calculation to real, verifiable code execution rather than trusting the model's own arithmetic produces exact, reproducible results instead of approximate or occasionally wrong ones.
Prompt Engineering Writing Task Descriptions Precise Enough for Autonomous Execution
▸

The task descriptions shown are notably long and explicit — far more detailed than a typical single-turn chat prompt — because there's no human in the loop to catch ambiguity mid-execution. Key techniques observed:

  • Emphasis markers (e.g. double asterisks around "generate Python code," "crucially") — used deliberately to make critical instructions stand out to the model, the same way a human skimming a spec would notice bolded text
  • Explicit global variable contracts — instructing agents to create/update specific named variables (shared_df, X_train, y_test, etc.) in a shared execution scope, since later agents/tasks depend on those exact variables existing
  • "Crucially, update the original DataFrame" — an explicit fix after observing the agent's first attempt created a NEW DataFrame instead of updating the shared one in place, breaking the downstream pipeline
  • Precise expected_output — describing exactly what successful completion looks like (specific print statements, specific confirmations) so the agent has an unambiguous stopping condition

Risk Flag — Iteration Was Required, Not One-Shot

The instructor explicitly notes going through "multiple iterations back and forth" to refine task descriptions — the first version of the pipeline didn't work correctly (the DataFrame-not-updated bug is a direct example). This is worth taking seriously: multi-agent autonomous systems are NOT reliably one-shot correct on a first attempt, even with careful upfront design — budget for observed-failure-driven prompt iteration as a normal part of building any such system, not an exception.

Active Recall: What specific bug required the task description to be revised with a "crucially, update the original DataFrame" instruction? tap to reveal
The analyst/preprocessor agent's first attempt at one-hot encoding created a NEW, separate DataFrame with the encoded columns, rather than updating the shared_df variable in place — breaking the pipeline since downstream tasks (train/test split, modeling) expected the transformations to be reflected in the same shared_df variable they'd reference. The fix was adding explicit emphasis instructing the agent to update the original shared variable, not create a separate one.
Security Giving an AI Agent the Ability to Execute Code — Worth Pausing On
▸

The instructor explicitly flags, before running the assembled crew, that this "imposes risk to your computer" — an LLM is autonomously generating and then actually executing Python code on the local machine via the notebook code executor tool, with no human review step between code generation and execution.

Risk Flag — Real, Not Hypothetical

This is the second explicit "this could go wrong" warning across this course's agentic projects (the first being the n8n module's Google Sheets delete-access warning). Arbitrary code execution by an autonomous agent is a materially different risk category from an agent calling a scoped, read-only tool — code execution can, in principle, do anything the host process can do. For any production use of this pattern, sandboxing (containerized/ephemeral execution environments, resource limits, no network/filesystem access beyond what's needed) would be a hard requirement, not an optional hardening step.

Architect's Lens

Worth connecting this directly to the Docker notes studied earlier — a properly isolated, ephemeral container is exactly the kind of sandbox that makes "let an agent execute arbitrary code" a defensible pattern rather than a reckless one. If this pattern were ever proposed for a real Optimus tool (an agent that writes and runs its own analysis code against production-adjacent data), the non-negotiable requirement would be: code execution happens in a disposable, network-isolated container with no access to anything beyond the specific dataset it's meant to analyze — never directly on a developer's or a production host's local environment.

Active Recall: What category of risk does giving an agent arbitrary code-execution ability introduce, that a scoped API tool (like a search or calendar tool) doesn't? tap to reveal
Arbitrary code execution can, in principle, do anything the host process/environment is capable of — read/write any accessible file, make any network call, consume unbounded resources — whereas a scoped API tool is limited to whatever specific, narrow actions that particular API exposes. This is why arbitrary code execution needs sandboxing (isolated, ephemeral, resource-limited environments) as a hard requirement for any production use, not just careful prompting.
Result Running the Crew — What Actually Happened
▸

With verbose=True, the full execution trace is visible: the Planner agent produces a numbered plan → the Analyst/Preprocessor agent generates and executes preprocessing code (visibly matching the manual notebook's steps: get_dummies, train_test_split, etc.) → the Modeler/Evaluator agent trains a Random Forest, evaluates it, and reports feature importance.

Final agent-produced results (R²≈0.78, RMSE≈286, price as top feature at ≈0.78 importance) closely matched the manually-built Random Forest's results (R²≈0.80) — a genuine validation that the automated crew reproduced equivalent-quality work to the hand-built pipeline, not just superficially similar-looking output.

Architect's Lens

The close numeric match between manual and agent-automated results is the actual proof point of this whole project — anyone can generate plausible-looking code; whether the automated pipeline produces genuinely comparable numerical results to a known-correct manual baseline is what separates a real validation from a demo. Worth using this same discipline for any Optimus automation candidate: don't just check "did the agent's output look reasonable," check "does it match a known-correct baseline within an acceptable tolerance."

The crew's final numeric results (R², RMSE, feature importance rankings) were compared directly against the KNOWN-CORRECT manually-built Random Forest results from earlier in the project, and closely matched them (R²≈0.78 vs ≈0.80) — proving the automated pipeline reproduced genuinely equivalent-quality analysis, not just code that superficially resembled a correct solution without actually matching known-good numbers.
Wrap-up The Honest Conclusion — Augmentation, Not Replacement
▸

The project's closing framing is notably measured rather than hyperbolic: CrewAI agents won't fully replace data scientists — human intuition is still needed to design the agent system itself, debug it when it goes wrong (as the DataFrame bug demonstrated), and validate results against domain knowledge. The stated position: "you still need humans in tandem with AI agents... but without AI agents you will definitely be left behind."

Questions worth carrying forward

  • Across the three multi-agent frameworks now studied (n8n visual workflows, OpenAI Agents SDK + MCP, CrewAI role-based crews) — which would you reach for first for a realistic Optimus data analysis automation task, and does the answer depend more on the task's complexity or on who needs to maintain the resulting system afterward (engineers vs. non-engineers)?
  • Given the explicit "multiple iterations required, not one-shot correct" honesty in this project — how would you budget realistic development time for a similar internal agentic tool, versus the (often optimistic) time estimates a vendor or excited team member might propose?
  • The code-execution risk flag here and the Google Sheets delete-risk flag from the n8n notes are the same underlying category (agent with real-world write/execute power) — would it be worth drafting one unified internal "agentic tool safety checklist" covering sandboxing, least-privilege scoping, and human-in-the-loop checkpoints, applicable across all these frameworks rather than re-deriving the same principles project by project?
