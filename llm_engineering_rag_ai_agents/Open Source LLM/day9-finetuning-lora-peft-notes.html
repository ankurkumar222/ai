Architects Lab · LLM Fine-Tuning Project

Fine-Tuning Open-Source LLMs: PEFT, LoRA & Financial Sentiment Classification

Notes from a hands-on fine-tuning project — taking a small open-source model (Gemma 1B) from zero-shot baseline to a LoRA-fine-tuned sentiment classifier on financial news, using Hugging Face Transformers, PEFT, and TRL's SFT Trainer. Structured for a Senior Engineering Manager building parallel intuition to your multi-LLM bootcamp work — the emphasis is on what's reusable production reasoning versus what's ML-research detail.
Framing Why Fine-Tune Instead of Training From Scratch?
▸
Think First: training a base LLM from scratch cost the original lab hundreds of millions of dollars. Fine-tuning starts from that same base model. What does it actually mean to "reuse" hundreds of millions of dollars of work with a tiny dataset of your own? tap to reveal
It means you're not teaching the model language, grammar, or general world knowledge again — all of that stays exactly as it was, frozen. You're only nudging a small slice of it toward a specific behavior using your much smaller dataset. Same architecture, same starting weights — the fine-tuning data reshapes what the model reaches for, not what it fundamentally knows. That's the entire economic case for fine-tuning existing: you get to stand on hundreds of millions of dollars of prior training for the cost of a much smaller, targeted dataset.

Take a pre-trained, general-purpose LLM and adapt a small slice of it using a much smaller, task-specific dataset — turning a generalist into a specialist.

 BASE MODEL (generalist, cost $100M+ to train, frozen)
       |
       |  asked: "joint pain + skin sensitivity?"
       v
 vague answer: "could be an allergy"

 SAME base model  +  fine-tuned on medical reports/notes
       |
       |  asked the SAME question

 specific answer: "could be lupus -- see a rheumatologist"

Architect's Lens

Think First: you already reason about "generalist platform, specialist configuration" in fintech — a rules engine tuned by config to act like a specialist tool. Where does that analogy with fine-tuning break down, if anywhere? tap to reveal

It holds structurally — the "engine" stays the same, only a targeted slice gets adjusted, whether that's config or model weights. It breaks down on predictability: a config change in a rules engine does exactly what you wrote, every time. A fine-tune reshapes probabilistic behavior — you're nudging what the model tends to reach for, not programming an exact rule, so the same "specialist configuration" can behave differently across similar inputs in a way a rules engine never would. Worth remembering that distinction before treating a fine-tuned model with the same certainty you'd give a configured rules engine.

Tech Stack The Toolchain — PEFT, TRL, Quantization, GPU
▸
Think First: running a model (inference) worked fine on a free-tier GPU, even a CPU in a pinch. Fine-tuning the SAME model absolutely requires a real GPU. What's actually different about the two workloads that makes one so much heavier than the other? tap to reveal
Inference is a single forward pass with frozen weights — plug in the input, read off the output, done. Fine-tuning adds backpropagation: compute how wrong the prediction was against the true label, then push that error backward through every layer to compute exactly how each weight should change. That's a massive matrix-multiplication workload running in both directions, repeated over every training example, every epoch — categorically heavier than a single forward pass, which is why a CPU can limp through inference but would take days on even simple fine-tuning.
ToolRole
Hugging Face TransformersLoad pre-trained models and tokenizers (Gemma, DeepSeek, etc.)
PEFT (Parameter-Efficient Fine-Tuning)Adapt large models by training only a small subset of parameters — makes fine-tuning affordable on consumer/free-tier GPUs
TRL (Transformer Reinforcement Learning)Full training toolkit; here used for its SFT (Supervised Fine-Tuning) Trainer — also supports DPO, reward modeling, GRPO
bitsandbytes4-bit quantization — stores weights in 4 bits instead of the usual 32, cutting memory dramatically with minimal quality loss
scikit-learnEvaluation: accuracy, precision, recall, F1, confusion matrix

Rough Sketch

 INFERENCE (running the model)     FINE-TUNING (training the model)
 -----------------------------     ---------------------------------
 input --> forward pass -->        input --> forward pass -->
 output                            output
 (weights frozen, one              compare to TRUE label
  direction, done)                       |
                                          v
                                    push error BACKWARD through
                                    every layer (backpropagation)
                                          |
                                          v
                                    update weights
                                    (repeat per example, per epoch)
 light enough for a CPU            needs a real GPU (T4 used here)

 toolchain, each piece's job:
   Transformers  -> load model + tokenizer
   PEFT          -> train only a SMALL slice of parameters
   TRL / SFTTrainer -> the actual training loop
   bitsandbytes  -> 4-bit quantization (32 bits -> 4 bits,
                     ~8x smaller, "surprisingly little" quality loss)
   scikit-learn  -> accuracy / precision / recall / F1 / matrix

Environment: Google Colab, Tesla T4 GPU (free tier is enough for this project's scale).

Architect's Lens

Think First: 4-bit quantization gives an 8x memory reduction for "surprisingly little" quality loss. If quantization is that cheap a win, why would anyone ever train or run a model at full 32-bit precision at all? tap to reveal

Because "surprisingly little" quality loss isn't zero, and it compounds. A single quantized inference pass loses a little precision that rarely matters. But during TRAINING, small precision errors accumulate across millions of gradient updates, and can measurably hurt the final model — which is exactly why quantization here is mainly used for loading/inference-time memory savings, while the LoRA weights being trained are still adjusted at higher precision. The lesson: a precision-vs-cost trade-off that's nearly free for one workload (inference) can be much more costly for another (training) — the same discipline as knowing which database queries can tolerate an approximate index and which need exact precision.

Data The Dataset — Financial News Sentiment, and the Imbalance Problem
▸
Think First: a model could hit 70% "accuracy" on this dataset just by always guessing "positive" if positive samples are the majority class. Before reading further — does a high accuracy number alone tell you whether the model actually learned to classify negative and neutral sentiment, or could it be hiding total failure on those classes? tap to reveal
It can absolutely hide total failure. Accuracy is a single blended number across all classes — a model that always guesses the majority class scores deceptively high on accuracy while being useless on the minority classes. This dataset has ~1,300 positive vs. ~500 negative samples, exactly the setup where that trap fires. You only catch it by looking at PER-CLASS numbers — precision, recall, F1, and the confusion matrix — not the one headline accuracy figure.

~4,800 rows: text (a news sentence) + sentiment (positive/negative/neutral). Split 90/10 train/test, shuffled first, fixed seed for reproducibility.

        |

        |
        v

Risk Flag

A model can look accurate while quietly failing the minority classes. Same shape as fraud detection: fraud is always rare, so "99.9% accurate" can mean "predicts not-fraud every time" — always check per-class recall, not the headline number.

Architect's Lens

Think First: fraud detection has the exact same imbalance shape — fraud is always the minority class. If a fraud model reports "99.9% accurate," what's the FIRST follow-up question you'd ask before trusting that number? tap to reveal

What's the recall on the fraud class specifically — not the accuracy, the fraud-class recall. A model that predicts "not fraud" on literally every transaction would already score 99.9%+ accuracy if fraud is rare, while catching zero fraud, which makes the model worthless despite the impressive headline number. The right follow-up isn't "how accurate" but "how many of the actual fraud cases did it catch, and how many false alarms did it raise" — precision and recall on the minority class, not the blended average. Same discipline this section teaches, just with real money on the line.

Formatting Chat Templates — Speaking the Model's Native "Language"
▸
Think First: Gemma and DeepSeek each expect their own special-token format — mismatched, training on the wrong one won't crash, it'll just quietly teach the model something slightly wrong. Why would a model even care about matching its OWN original format, when the training text and label are otherwise identical either way? tap to reveal
Because the model didn't just learn language during pretraining — it learned to recognize ITS OWN turn markers as the signal for "this is where I should pay attention / this is where my reply starts." Feed it text formatted for a different model's tokens, and those markers are meaningless noise to it — it never learned what they mean. The words are the same, but the structural cues the model relies on to separate "instruction" from "my answer" are gone or wrong, which degrades training even though nothing crashes.

Raw text/sentiment pairs must be reformatted into the exact structure each model was trained on, using tokenizer.apply_chat_template() — like a movie script with explicit markers for who's "speaking."

Gemma format:
<bos><start_of_turn>user
Classify the sentiment... [sentence]<end_of_turn>
<start_of_turn>model
positive<end_of_turn>

DeepSeek format (different special tokens entirely):
<special token> beginning-of-sequence marker
Classify the sentiment... [sentence]
[model turn marker]
positive [end-of-sequence marker]

Rough Sketch

 raw pair:  text="Stock X jumps", sentiment="positive"
                       |
                       v
         tokenizer.apply_chat_template(...)
                       |
          /------------+------------\
          v                          v
       Gemma model                DeepSeek model
   <start_of_turn>user...      <special token>...
   <start_of_turn>model            [model turn marker]
   positive<end_of_turn>           positive [eos]

 SAME call interface, COMPLETELY different actual output --
 each model only recognizes ITS OWN turn markers

 tokenize=False --> readable text (for building training data)
 tokenize=True  --> converts straight to token IDs

Architect's Lens

Think First: the Vercel course's OpenAI-style client hid every provider's internal formatting differences behind one consistent interface. Here, the SAME kind of interface (apply_chat_template) exists — but does it actually hide the difference the same way, or does it just relocate where you need to notice it? tap to reveal

It relocates the problem rather than removing it. A chat API client hides formatting differences because the provider handles formatting server-side — you never see it. apply_chat_template() does the OPPOSITE: it exposes the model-specific format directly into text you're about to train on, so you have to know which model you're targeting before calling it, or you'll silently generate the wrong training format. If your multi-LLM bootcamp work ever needs to fine-tune across model families, this is exactly the layer where "same SDK shape" stops meaning "same actual behavior" — and where explicit per-model handling becomes non-optional.

Baseline Zero-Shot Evaluation — Measuring Before You Improve
▸
Think First: before spending GPU time fine-tuning anything, this project first measures the UN-fine-tuned model's performance. If you skipped that step and went straight to fine-tuning, what specific question would you be unable to answer afterward? tap to reveal
You'd have no way to tell whether fine-tuning actually helped. Without a baseline, "the fine-tuned model got 62% accuracy" is a number floating with no reference point — good, bad, or no different from doing nothing? Section 8 later shows the fine-tuned model actually performed WORSE than baseline in this project's live run — a fact that would be invisible without this exact baseline step. "Measure before you optimize" isn't ML ceremony, it's the only way to know if the optimization worked at all.

Base Gemma-1B, zero-shot (no examples, just an instruction), run on the test set before any fine-tuning: ~45–46% accuracy, weak recall (0.16) on the neutral class.

Rough Sketch

 base Gemma-1B, ZERO fine-tuning, run on test set:
   accuracy: ~45-46%
   neutral-class recall: 0.16  (very weak)
   212 out of ~480 misclassified

 this number is the LINE fine-tuning has to beat --
 without it, "fine-tuned = 62% accuracy" means NOTHING
 (better? worse? no idea, without this baseline)

 PROMPT SENSITIVITY EXPERIMENT:
   detailed prompt (lists valid labels explicitly)
        --> model answers positive/negative/neutral, reliably

   simplified prompt (label list removed)

            of the three valid classes anymore

   conclusion: SMALL models are especially sensitive to exact

Architect's Lens

Think First: dropping ONE detail (an explicit label list) broke a small model's output entirely. If cost pressure ever pushed an Optimus tool toward a smaller/cheaper model, would you expect your EXISTING prompts (written for a frontier model) to just work, or to need real rework? tap to reveal

Expect real rework, not a drop-in swap. This finding shows tolerance for vague or implicit instructions shrinks with model size — a frontier model can often infer what you meant even from a loosely-worded prompt; a smaller model needs the constraint spelled out explicitly or it drifts into unreliable output. Treat any move to a smaller/cheaper model as a prompt-engineering project in its own right, not just a config change — the same discipline as "establish a baseline before you optimize," applied to the prompt itself, not just the model weights.

Core Concept LoRA — The Math Behind "Fine-Tune 0.3% of the Model"
▸
Think First: a weight matrix has 200 million numbers. LoRA claims it can approximate the needed CHANGE to that matrix using two much smaller matrices instead. Before seeing the math — does that sound like it should lose real capability, or is there a reason a "smaller" update could still work well? tap to reveal
It does lose some theoretical capability — a low-rank update genuinely can't represent every possible change the full matrix could. But the bet LoRA makes (and that works in practice) is that the ACTUAL change needed for most fine-tuning tasks doesn't need the full matrix's expressiveness — task adaptation tends to live in a much lower-dimensional space than the full weight matrix. Trading some theoretical capacity for an ~833x parameter reduction turns out to be a very good deal for most real tasks, which is exactly why LoRA works well in practice, not just in theory.

LoRA avoids updating all of a model's weights directly. For a given weight matrix, it trains two small matrices (A and B) whose product approximates the needed change.

Worked example from the lecture:
  Original weight matrix:     10,000 × 20,000 = 200,000,000 parameters
  LoRA with rank r = 8:
    Matrix A: 10,000 × 8   =      80,000 parameters
    Matrix B:      8 × 20,000 =  160,000 parameters
    Total:                   =  240,000 parameters

  Reduction: 200,000,000 → 240,000  ≈ 833× fewer trainable parameters

Rough Sketch

 FULL FINE-TUNE                     LoRA (rank r=8)
 ---------------                    ---------------
 update ALL 200,000,000             freeze the original matrix
 numbers in the weight              add TWO tiny matrices:
 matrix directly                      A: 10,000 x 8   = 80,000
                                       B:      8 x 20,000 = 160,000
                                    train ONLY A and B (240,000)
                                    A x B approximates the update

 200,000,000  ---->  240,000   =  ~833x fewer trainable params

 REAL PROJECT RESULT (Gemma-1B, ~1 billion total params):
   only ~3 million trainable  =  0.29% of the whole model
   applied to attention layers (Q, K, V, O projections)
   everything else stays frozen

 rank (r) is a DIAL:
   higher r --> more capacity to adapt, more cost
   lower r  --> less capacity, cheaper/faster
   (tunable hyperparameter, not a fixed constant)

Architect's Lens

Think First: an 833x parameter reduction is the difference between "needs a datacenter" and "runs on a free Colab GPU." If AI/ML interviewers at Sarvam AI, PhonePe, or Razorpay asked you WHY that reduction doesn't just gut model quality, could you actually explain the mechanism — not just quote the ratio? tap to reveal

The honest answer: it's a low-rank approximation, mathematically the same family of idea as dimensionality reduction elsewhere in data engineering — the bet that the actual adaptation needed for a specific task lives in a much lower-dimensional space than the full weight matrix, so constraining the update to rank r still captures most of what matters. Being able to say that, rather than just citing "833x fewer parameters," is the difference between having memorized a number and understanding why LoRA is a legitimate engineering trade-off, not a trick — a real distinction an interviewer probing cost-efficient customization strategies would notice.

Training Running the Fine-Tune — SFT Trainer and Hyperparameters
▸
Think First: after training, the pipeline saves only the small LoRA matrices (A and B) — NOT a full new copy of the 1-billion-parameter model. What does that imply about what you actually need on disk (and at inference time) to use a fine-tuned model? tap to reveal
You need the original frozen base model PLUS the tiny adapter — the adapter alone is useless without the base model it was trained against, since it only represents a small delta, not the whole capability. At inference time, the base model and adapter are loaded and combined to produce the fine-tuned behavior. This is also why LoRA adapters are so easy to distribute and swap: the saved artifact is tiny (megabytes, not gigabytes), so you could keep several task-specific adapters around for the same base model without storing multiple full copies of it.
1. Load base model (already loaded, quantized)
2. Wrap with LoraConfig (rank r, target attention modules, dropout)
3. Get PEFT model = base model + LoRA adapters attached
4. Set TrainingArguments: output dir, learning rate, epochs,
   batch size, logging frequency (every 25 steps here)
5. SFTTrainer(model, training_args, train_dataset, peft_config)
6. trainer.train()
7. Save the adapter (NOT a new full model — just the small
   LoRA weight deltas, stored separately)

Rough Sketch

 base model (quantized, frozen)
        |
        v  LoraConfig(rank r, target modules, dropout)
 PEFT model = base model + LoRA adapters attached
        |
        v  SFTTrainer(model, args, train_dataset, peft_config)
        v  trainer.train()

 training loss over ONE epoch:
   3.5 -> 2.0 -> 1.7 -> 1.6 -> 1.4 (bumpy, not smooth --
                                     expected/noisy for one epoch,
                                     not a red flag on its own)
        |

 SAVE: only the small adapter (A, B matrices) --
       NOT a whole new copy of the model

 EPOCH COUNT MATTERS:
   1 epoch  -----> "to keep cost down" -- risk: UNDER-trained,
                    can come out WORSE than zero-shot baseline
   4-5+ epochs --> typically needed for real improvement
   too many epochs, no early stopping --> OVERFITTING risk
                    (memorizes training data, generalizes worse)

Architect's Lens

Think First: this run used exactly one epoch "to keep cost down," and — spoiler for the next section — it came out worse than doing nothing. If cost is always a real constraint, is "run fewer epochs" ever actually cheaper once you count the whole picture? tap to reveal

Often not, once you count the whole picture. A fine-tune that performs worse than the untouched base model isn't a cheaper result — it's a wasted training run plus the cost of catching that it underperformed (which requires the baseline comparison from Section 5) plus the cost of the eventual re-run at 4-5 epochs to actually get an improvement. "Fewer epochs" only saves money if you were always going to check against baseline and stop the moment it's clearly not helping. Skipping that check is what turns "cheaper" into "wasted spend that still needs redoing" — the real lesson isn't epoch count, it's never shipping a fine-tune without the baseline comparison to justify it.

Result The Fine-Tuned Model Performed Slightly WORSE — And That's the Real Lesson
▸
Think First: before reading the numbers below — given everything you now know about one-epoch training being risky, do you predict the fine-tuned model beat the zero-shot baseline, matched it, or lost to it? And if it lost, does that mean LoRA/fine-tuning "doesn't work"? tap to reveal
It lost — accuracy dropped by about 0.04 versus baseline, misclassifications rose from 212 to 258. But that does NOT mean fine-tuning doesn't work. It means one epoch on this dataset wasn't enough training for the LoRA adapters to converge on anything useful — under-training, not a flaw in the approach. A separate longer run (4-5 epochs) did show real improvement. The honest lesson: fine-tuning is an experiment with a real chance of making things worse, not a step that automatically helps just because you did it.

After combining the base model with the trained adapter and re-running the same test-set evaluation: accuracy dropped by about 0.04 versus baseline. Misclassifications rose from 212 to 258.

Architect's Lens

Think First: this project could have just NOT shown you the failed run and only presented the successful 4-5 epoch version. Why is watching the failure — with the honest, worse-than-baseline numbers — more valuable to you than seeing only the polished success? tap to reveal

Because the failure is the actual production lesson, and the success alone would have hidden it. Seeing only a winning result teaches "fine-tuning improves things" — a claim that's true often enough to be dangerous, because the one time it's false (under-training, bad data, wrong rank) is exactly when you need to have already internalized that fine-tuning can regress performance. Watching it fail live, with real numbers, builds the actual discipline this project is trying to teach: never assume "we fine-tuned it" means "it's better" — always demand the baseline comparison and a go/no-go decision based on measured results, the same rigor you'd want for any other model-change rollout.

Wrap-up Project Recap — What Was Actually Learned
▸
Think First: across this whole project — imbalanced data, prompt sensitivity, LoRA's rank trade-off, the under-trained result — one instinct kept showing up in different clothes. What's the ONE habit that would have caught every single one of these issues, if you'd applied it consistently? tap to reveal
Measure before you trust. Check per-class numbers instead of trusting accuracy (Section 3). Test the model's actual behavior before assuming a prompt is "good enough" (Section 5). Compare against a real baseline before assuming fine-tuning helped (Section 8). Every failure mode in this project is the same root cause wearing a different costume: trusting a plausible-looking result instead of measuring it against a reference point. That's the transferable skill here, more than any specific LoRA math.
