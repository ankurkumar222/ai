Fine-Tuning Open-Source LLMs: PEFT, LoRA & Financial Sentiment Classification

Notes from a hands-on fine-tuning project — taking a small open-source model (Gemma 1B) from zero-shot baseline to a LoRA-fine-tuned sentiment classifier on financial news, using Hugging Face Transformers, PEFT, and TRL's SFT Trainer. Structured for a Senior Engineering Manager building parallel intuition to your multi-LLM bootcamp work — the emphasis is on what's reusable production reasoning versus what's ML-research detail.
Framing Why Fine-Tune Instead of Training From Scratch?
▸

Core idea: take a pre-trained, general-purpose LLM (already trained on internet-scale data, costing the original lab hundreds of millions of dollars) and adapt a small subset of its parameters using a much smaller, task-specific dataset — turning a generalist into a specialist.

Illustrative example given: a base LLM asked about joint pain + skin sensitivity gives a vague "could be an allergy" answer. The same base model, fine-tuned on medical reports and patient notes, responds with a specific, clinically-relevant hypothesis ("could be lupus — see a rheumatologist"). Same architecture, same starting weights — the fine-tuning data reshapes what the model reaches for.

Architect's Lens

This is the same "generalist platform, specialist configuration" pattern you already reason about in fintech systems — a general-purpose rules engine or workflow platform tuned with domain-specific config to behave like a specialist tool, without rebuilding the underlying engine. Fine-tuning is that same idea applied to model weights instead of config files: the "engine" stays the same 1B-parameter transformer; only a tiny, targeted slice of it gets adjusted.

Active Recall: What's the key difference between fine-tuning and training from scratch? tap to reveal
Training from scratch means learning all model weights from nothing, requiring massive data and compute. Fine-tuning starts from an already-trained model and adjusts a much smaller set of weights (or a small added set, as with LoRA) using a much smaller, task-specific dataset — reusing everything the base model already learned.
Tech Stack The Toolchain — PEFT, TRL, Quantization, GPU
▸
ToolRole
Hugging Face TransformersLoad pre-trained models and tokenizers (Gemma, DeepSeek, etc.)
PEFT (Parameter-Efficient Fine-Tuning)Adapt large models by training only a small subset of parameters — makes fine-tuning affordable on consumer/free-tier GPUs
TRL (Transformer Reinforcement Learning)Full training toolkit; here used for its SFT (Supervised Fine-Tuning) Trainer — also supports DPO, reward modeling, GRPO
bitsandbytes4-bit quantization — stores weights in 4 bits instead of the usual 32, cutting memory dramatically with minimal quality loss
scikit-learnEvaluation: accuracy, precision, recall, F1, confusion matrix

Environment: Google Colab with a Tesla T4 GPU (paid tier used here for extended runs; free tier T4 access is sufficient for this project's scale).

Architect's Lens

Quantization is the detail worth internalizing even outside ML work: storing weights in 4 bits instead of 32 is an 8x memory reduction for "surprisingly little" quality loss — a classic precision-vs-cost trade-off you'd recognize from database indexing or numeric storage decisions in fintech systems. It's exactly the kind of cost lever worth knowing exists when someone on your team proposes "we need a bigger GPU" — the real question is often "have we quantized yet?" before "do we need more hardware?"

Active Recall: Why is a GPU absolutely required for fine-tuning, when it wasn't strictly required for running inference on the same model? tap to reveal
Fine-tuning requires backpropagation and gradient updates — computing prediction error against ground truth and adjusting weights accordingly, which is extremely matrix-multiplication-heavy. Inference on a pre-trained model is just a single forward pass with frozen weights (no gradient calculation), which is far less computationally expensive — a CPU can limp through inference but would take days for even simple fine-tuning.
Data The Dataset — Financial News Sentiment, and the Imbalance Problem
▸

~4,800 rows from a Hugging Face dataset, two columns: text (a news sentence) and sentiment (positive / negative / neutral). Split 90/10 train/test with a fixed random seed (42) for reproducibility, and shuffled first so the model doesn't learn spurious positional patterns.

A count plot revealed class imbalance: roughly 1,300 positive samples vs. ~500 negative — the minority classes are underrepresented relative to positive.

Risk Flag

With imbalanced data, a model can achieve deceptively high accuracy simply by leaning toward the majority class while doing poorly on minority classes — the analogy given: a self-driving car trained on 10 million cars but only 1,000 bikes will perform much worse recognizing bikes, even if overall accuracy looks fine. This is why accuracy alone is flagged as insufficient here — precision, recall, F1, and the confusion matrix are needed to see per-class performance clearly.

Architect's Lens

This is a direct analogue to fraud-detection or anomaly-detection problems in fintech — fraud cases are always the minority class, and a model that's 99.9% "accurate" by predicting "not fraud" every time is useless. The same discipline applies: never evaluate an imbalanced-class model on accuracy alone, always look at per-class precision/recall and the confusion matrix, and consider over/undersampling if the imbalance is severe.

Active Recall: Why can accuracy alone be misleading on an imbalanced dataset? tap to reveal
Because a model can score high accuracy simply by predicting the majority class most or all of the time, while performing poorly on minority classes — accuracy doesn't reveal that per-class weakness. Precision, recall, F1, and the confusion matrix expose it by showing performance broken down per class.
Formatting Chat Templates — Speaking the Model's Native "Language"
▸

Raw text/sentiment pairs must be reformatted into the exact conversational structure each model was originally trained on, using tokenizer.apply_chat_template(). Analogy used: it's like a movie script — explicit turn markers for who's "speaking" (system instruction, user input, model response).

Gemma format:
<bos><start_of_turn>user
Classify the sentiment... [sentence]<end_of_turn>
<start_of_turn>model
positive<end_of_turn>

DeepSeek format (different special tokens entirely):
<special token> beginning-of-sequence marker
Classify the sentiment... [sentence]
[model turn marker]
positive [end-of-sequence marker]

Key parameter: tokenize=False keeps the output as readable text (for building the training format); flipping it to True immediately converts it into token IDs — useful to see directly why this setting matters.

Architect's Lens

The fact that Gemma and DeepSeek use entirely different special-token conventions is a concrete, hands-on illustration of exactly the "same SDK shape, different provider internals" abstraction problem flagged in your Vercel course notes (Day 1) — the OpenAI-style client interface hides this completely, but underneath, every model family has its own trained-in formatting contract. If your multi-LLM bootcamp work ever needs to fine-tune or closely control prompt structure across model families, this chat-template layer is exactly where that portability breaks down and needs explicit handling per model.

Active Recall: Why does the Dockerfile-style "same shape, different internals" problem from the Vercel course reappear here with Gemma vs. DeepSeek? tap to reveal
Because each model family is trained on its own specific chat-template format with its own special tokens for marking turns, system prompts, and end-of-sequence — even though the same Hugging Face `apply_chat_template()` call interface works for both, the actual formatted output (and what the model expects) differs completely between Gemma and DeepSeek.
Baseline Zero-Shot Evaluation — Measuring Before You Improve
▸

Before any fine-tuning, the base Gemma-1B model is run directly on the test set (zero-shot — no examples given in the prompt, just an instruction) to establish a baseline. Result: ~45–46% accuracy, with notably weak recall (0.16) on the neutral class — expected from a small, 1-billion-parameter model with no task-specific adaptation.

212 out of ~480 test samples were misclassified (visualized via confusion matrix heatmap) — establishing exactly the number fine-tuning is meant to improve on.

Prompt Sensitivity — A Real Finding, Not Just an Exercise

A follow-up experiment simplified the zero-shot system prompt (removing the explicit list of valid labels) and the model started producing "unknown" outputs — responses that didn't match any of the three valid classes at all. Explicit conclusion: small models are especially sensitive to prompt wording for zero-shot tasks — precise, explicit instructions materially change reliability, not just quality.

Architect's Lens

"Establish a baseline before you optimize" is universal engineering discipline, not ML-specific — the same rule you'd apply before optimizing a slow query or a service's latency. The prompt sensitivity finding is worth carrying directly into your own Optimus/idfc-coder prompt template work: if smaller or cheaper models are ever considered for cost reasons, expect them to need noticeably more explicit, constrained prompting than a frontier model would — the tolerance for vague instructions shrinks with model size.

Active Recall: What happened when the zero-shot system prompt was made more generic (no explicit label list), and what does that imply? tap to reveal
The model started producing "unknown" responses — outputs that didn't match any of the three valid sentiment labels. This implies smaller models are highly sensitive to exact prompt wording for zero-shot classification, and precise, explicit instructions are necessary for reliable structured output.
Core Concept LoRA — The Math Behind "Fine-Tune 0.3% of the Model"
▸

LoRA (Low-Rank Adaptation) avoids updating all of a model's billions of weights directly. Instead, for a given weight matrix, it introduces two small trainable matrices (A and B) whose product approximates the needed weight update — dramatically reducing the number of trainable parameters.

Worked example from the lecture:
  Original weight matrix:     10,000 × 20,000 = 200,000,000 parameters
  LoRA with rank r = 8:
    Matrix A: 10,000 × 8   =      80,000 parameters
    Matrix B:      8 × 20,000 =  160,000 parameters
    Total:                   =  240,000 parameters

  Reduction: 200,000,000 → 240,000  ≈ 833× fewer trainable parameters

Real result on Gemma-1B in this project: of the model's ~1 billion total parameters, only ~3 million (0.29%) were made trainable after applying LoRA to the attention layers (Q, K, V, O projections) — everything else stays frozen at its pre-trained values.

Higher rank (r) = more trainable parameters = more capacity to adapt, but also more compute/memory cost — a tunable hyperparameter, not a fixed constant.

Architect's Lens

This is a beautifully concrete example of a low-rank approximation reducing a large problem to a tractable one — mathematically the same family of idea as dimensionality reduction techniques used elsewhere in data engineering. For cost-conscious production reasoning: LoRA is precisely why fine-tuning open-source models has become financially viable for teams without frontier-lab budgets — a ~833x parameter reduction is the difference between "needs a datacenter" and "runs on a single free-tier Colab GPU." Worth knowing as a talking point if AI/ML interview conversations (Sarvam AI, PhonePe, Razorpay) ever probe cost-efficient customization strategies.

Active Recall: In the worked example, why does LoRA with rank 8 reduce a 200-million-parameter matrix to only 240,000 trainable parameters? tap to reveal
Instead of directly updating the full 10,000×20,000 weight matrix, LoRA introduces two much smaller matrices — A (10,000×8) and B (8×20,000) — whose product approximates the needed weight change. Adding their parameter counts (80,000 + 160,000 = 240,000) is vastly smaller than the original 200 million, because the "rank" (8) constrains how much information the update matrices can carry, trading some adaptation capacity for a massive efficiency gain.
Training Running the Fine-Tune — SFT Trainer and Hyperparameters
▸ 
1. Load base model (already loaded, quantized)
2. Wrap with LoraConfig (rank r, target attention modules, dropout)
3. Get PEFT model = base model + LoRA adapters attached
4. Set TrainingArguments: output dir, learning rate, epochs,
   batch size, logging frequency (every 25 steps here)
5. SFTTrainer(model, training_args, train_dataset, peft_config)
6. trainer.train()
7. Save the adapter (NOT a new full model — just the small
   LoRA weight deltas, stored separately)

Training loss observed over one epoch: started ~3.5, dropped to ~2.0, then 1.7, 1.6, ticking back up slightly to 1.4 by the end — explicitly flagged as expected/noisy behavior for a single epoch, not a red flag on its own.

Risk Flag — Epoch Count Matters a Lot Here

Only one epoch was run for the live demonstration ("to keep cost down"). The instructor explicitly notes real improvement typically requires 4–5+ epochs, and that with too few epochs, fine-tuned performance can come out worse than the zero-shot baseline — which is exactly what happened in this project's live run (see next section). Overfitting is also flagged as a risk at the other extreme — too many epochs without a validation-based early-stopping check can cause the model to memorize training data and generalize worse.

Architect's Lens

The "we ran one epoch for cost reasons and got a worse result than baseline" outcome is a genuinely useful production lesson, not a course failure: fine-tuning has a real cost/quality curve, and an under-trained fine-tune can be actively harmful compared to just using the base model untouched. Worth remembering as a checkpoint before ever shipping a fine-tuned model: always compare against the zero-shot/base-model baseline explicitly, and don't assume "we fine-tuned it" implies "it's better."

Active Recall: What does saving a LoRA "adapter" actually save, as opposed to saving a full fine-tuned model? tap to reveal
It saves only the small LoRA weight matrices (A and B, and any other trained adapter parameters) — not a full copy of the entire base model. The base model stays untouched and frozen; at inference time, the adapter is loaded and combined with the base model to produce the fine-tuned behavior, keeping the saved artifact tiny compared to the full model.
Result The Fine-Tuned Model Performed Slightly WORSE — And That's the Real Lesson
▸

After combining the base model with the trained adapter and re-running the same test-set evaluation: accuracy dropped by about 0.04 versus the zero-shot baseline. Precision improved slightly on some classes, but recall worsened enough to drag overall accuracy down. Misclassifications in the confusion matrix increased from 212 to 258.

Explicitly attributed to under-training: only one epoch was run for the live demo; the instructor states that a longer run (4–5 epochs, done separately and provided as supplementary material) showed a real improvement over baseline.

Architect's Lens

This is arguably the single most valuable moment in the whole project for a production mindset: a live, honest demonstration that fine-tuning is not automatically an improvement — it's an experiment with its own failure modes (under-training here; overfitting is the opposite failure mode). The discipline this implies: fine-tuning needs the same rigor as any other model-change rollout — a held-out baseline comparison, and a go/no-go decision based on measured results, not an assumption that "we did the fine-tuning step, therefore it's better."

Wrap-up Project Recap — What Was Actually Learned
▸ 
1. Fine-tuning rationale: generalist → specialist, using a small
   task-specific dataset on top of a pre-trained base model
2. Tech stack: Transformers, PEFT, TRL/SFT Trainer, bitsandbytes
   (4-bit quantization), scikit-learn for evaluation
3. Data prep: load, inspect, train/test split, check class balance
4. Chat-template formatting: model-specific special tokens
   (Gemma vs. DeepSeek shown as contrasting examples)
5. Zero-shot baseline established BEFORE fine-tuning (~45-46% acc)
6. LoRA theory: low-rank matrices A/B approximate weight updates,
   reducing trainable parameters by orders of magnitude (here: 0.29%
   of the full model)
7. Training run via SFTTrainer, one epoch (demo-scale)
8. Evaluation showed a WORSE result than baseline — an honest
   lesson in under-training risk, not fine-tuning being ineffective
