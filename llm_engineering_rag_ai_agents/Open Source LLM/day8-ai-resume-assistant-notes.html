AI Resume & Cover Letter Assistant — Pydantic + OpenAI/Gemini

Notes from a hands-on project — a pipeline that compares a resume against a target job description, identifies gaps, generates a tailored resume with tracked changes, and drafts a matching cover letter, using Pydantic for structured output and both OpenAI and Gemini as swappable backends. Structured for a Senior Engineering Manager who is actively job hunting — this project maps directly onto your own Sarvam AI / PhonePe / Razorpay applications, not just an abstract exercise.
Framing What This Tool Actually Does — And the One Rule That Matters Most
▸

Pipeline: old resume + target job description → (1) gap analysis (what's missing, what matches, what's an under-highlighted strength) → (2) a tailored, rewritten resume with tracked additions/removals → (3) a matching, tone-appropriate cover letter.

The Non-Negotiable Rule — Stated Explicitly and Repeated

Every generated metric (percentages, growth numbers, "increased X by 30%") is fabricated by the LLM to sound impressive — none of it is real unless you already did it. The instructor repeats this warning multiple times: submitting an AI-embellished resume with numbers you can't back up is both unethical and a real risk if questioned in an interview. The tool's correct use is to surface phrasing and structure, and to flag genuine gaps — the human must verify every specific claim before it goes anywhere near a real application.

Architect's Lens

Given you're actively targeting AI/ML-focused roles, this is worth treating as more than a course exercise — it's a real tool you could adapt for your own applications this week. But the fabricated-metrics risk is exactly the kind of thing that would sink credibility fast in an interview at a company that takes AI engineering seriously (Sarvam AI, PhonePe, Razorpay would all likely probe specifics) — treat every AI-suggested number as a draft placeholder to replace with your own verified data, never as a fact to keep.

Active Recall: What is the single most important guardrail when using this kind of resume tool? tap to reveal
Never submit AI-generated quantitative claims (percentages, growth numbers, specific achievements) unless you can personally verify they're true and you actually did them. The LLM fabricates plausible-sounding metrics to make the resume more impressive, but they are not grounded in fact unless the human confirms and edits them — this is a human-in-the-loop requirement, not optional polish.
Pydantic 101 Why Structured Output Validation Matters
▸ 
from pydantic import BaseModel

class User(BaseModel):
    name: str
    age: int
    email: str

User(name="Mira Hero", age=30, email="mira@gmail.com")   # ✓ valid
User(name="Mira", age="not a number", email="...")        # ✗ raises
                                                            #   a validation error

Pydantic defines a data "blueprint" using Python type hints, then automatically validates that any data assigned to it matches — raising a clear error instead of silently accepting malformed data, and in many cases auto-converting compatible types. This replaces the earlier, weaker pattern of just describing the desired output format in plain-English prompt text and hoping the LLM complies.

Architect's Lens

This is the exact same principle as FastAPI's Pydantic request validation seen in the Vercel production course (Day 4's healthcare app) — the same library, same discipline, applied to LLM output here instead of API input. Worth recognizing as one unified pattern: wherever untrusted or generated data crosses a boundary into your system (an API request, an LLM response), Pydantic-style schema validation at that boundary is the fix, not manual parsing or hoping for the best.

Active Recall: What happens differently when you pass invalid data to a Pydantic model versus a plain Python dictionary? tap to reveal
A plain dictionary would silently accept whatever value you give it, regardless of type. A Pydantic model actively validates each field against its declared type hint and raises a clear validation error immediately if the data doesn't match (e.g. a string passed where an integer was expected) — catching the problem at the boundary instead of letting bad data flow silently into your application.
Integration Getting Structured JSON Directly From OpenAI
▸ 
class Destination(BaseModel):
    city: str
    country: str
    top_attractions: list[str]

response = client.beta.chat.completions.parse(
    model="gpt-4o",
    messages=[...],
    temperature=0,
    response_format=Destination      # ← the Pydantic model itself
)

The .beta.chat.completions.parse() method takes a Pydantic model directly as response_format — OpenAI returns output that's guaranteed to match that schema, instead of generating free text that you then have to hope parses correctly. A list-type field (top_attractions: list[str]) tells the model to return a collection, not a single value.

Active Recall: What's the practical benefit of passing a Pydantic model as response_format, versus just describing the desired JSON structure in the prompt text? tap to reveal
The API enforces the schema at generation time and returns validated, guaranteed-structured output — eliminating the risk of the model returning malformed JSON, missing fields, or wrong types that you'd otherwise have to catch and handle after the fact when relying purely on prompt instructions.

One function handles both plain-text and Pydantic-structured generation, branching on whether response_format was supplied. Default parameter values (model, temperature, max_tokens) mean callers only need to specify what differs from the default — the same "sensible defaults, override what you need" pattern seen across the FastAPI and LangChain projects.

Architect's Lens

This dual-mode function design (one function, two behaviors, selected by an optional parameter) is a clean, reusable pattern worth lifting directly for any internal Optimus wrapper around an LLM call — rather than maintaining two separate near-duplicate functions for "structured" and "unstructured" generation, a single well-documented function with an optional schema parameter keeps the call surface simple for callers while supporting both use cases.

Comparison OpenAI vs. Gemini — Same Prompt, Different Providers, Different Results
▸

Two near-identical generate functions (openai_generate, gemini_generate) accept the same prompt and produce comparable output — a direct, hands-on multi-provider comparison. Notable findings from the live tests:

  • Both models correctly followed the "results-driven metrics" instruction, but generated different specific numbers (100 vs. 50 blog posts) for the same underlying vague resume bullet — a direct illustration that these numbers are fabricated, not recalled facts.
  • At the same prompt, Gemini consistently picked up an added instruction (mention AI/prompt-engineering skills) that OpenAI sometimes missed on one run and caught on another — non-deterministic instruction-following even at fixed settings.
  • Cranking OpenAI's temperature to 1.6 (near the 0-2 range's upper bound) visibly degraded output — the model started drifting into other languages and incoherent text, a live demonstration of the "high temperature = erratic" warning from earlier lessons.

Architect's Lens

This is a very concrete data point for your multi-LLM bootcamp work: even with the same prompt, temperature, and task, provider behavior is not perfectly interchangeable or fully deterministic run to run. For any production pipeline (Optimus or otherwise) relying on a specific model to reliably follow an instruction, this argues for either explicit output validation (Pydantic, again) that catches when an instruction was missed, or a retry/self-check step, rather than trusting a single generation to consistently comply.

Active Recall: What happened to OpenAI's output when temperature was pushed to 1.6, and what does that confirm? tap to reveal
The output became visibly erratic — it started drifting into other languages and generating incoherent text. This confirms the general rule that pushing temperature toward the top of its range (near 2) sacrifices coherence for randomness/creativity, and for tasks like resume writing that need to stay factual and readable, a much lower temperature is appropriate.
Core Logic The Gap Analysis Function — The Heart of the Tool
▸

Prompt structure asks the model to produce four distinct sections in one pass:

  1. Key requirements extracted from the job description
  2. Relevant experience already present in the resume
  3. Gaps/mismatches — requirements not evidenced in the resume
  4. Potential strengths — resume content not explicitly requested, but valuable

The same function supports either OpenAI or Gemini via a simple if/elif branch on a model parameter — one interface, swappable backend, directly reusing the dual-provider pattern from Section 5.

Active Recall: Why does the gap analysis explicitly include a "potential strengths" section, not just "gaps"? tap to reveal
Because a resume may contain valuable, relevant experience that isn't literally listed as a job requirement but still strengthens the application — surfacing this helps the candidate deliberately highlight it, rather than only reacting defensively to what's missing.
Iteration Prompt Tuning — Surfacing AI/Prompt-Engineering Skills as a Strength
▸

A follow-up refinement adds an explicit instruction to the "potential strengths" section: highlight any AI-adjacent skills (prompt engineering, ChatGPT familiarity) as valuable, even if not literally requested in the job posting — reflecting how AI fluency is increasingly treated as a real hiring signal.

Result: Gemini consistently surfaced this addition; OpenAI was inconsistent — catching it on one run, missing it on a re-run with the identical prompt and inputs, only reliably appearing after the temperature was adjusted.

Architect's Lens

Directly relevant to your own resume/LinkedIn positioning: this project's own finding validates explicitly calling out AI/prompt-engineering fluency as a distinct, valued skill category — not assuming it's implied by "used ChatGPT for tasks." Given your idfc-coder and Optimus Project work, that's a concrete, evidenced example (leading AI adoption for 80+ microservices, prompt template design) that this tool's own logic would flag as a "potential strength" worth surfacing explicitly rather than burying in a generic bullet point.

Generation Producing the Tailored Resume — With Tracked Changes
▸

Feeding the original resume + job description + gap analysis into a resume-rewriting prompt produces two outputs: the updated resume text, and a separate markdown "diff" showing what was added/changed/removed — letting the human clearly review and approve every modification before using it, directly supporting the human-in-the-loop verification rule from Section 1.

Active Recall: Why generate a separate "diff" markdown alongside the updated resume, rather than just handing over the final rewritten version? tap to reveal
To make every change explicitly visible and reviewable — since the tool can fabricate plausible-sounding metrics or additions, the diff lets the human quickly scan exactly what was added, changed, or removed and verify or correct each claim before using the resume for a real application, rather than having to compare two full documents line by line.

Pipeline The Unified "Resume Rocket" Function
▸ 
def run_resume_rocket(resume: str, job_description: str):
    gaps = analyze_resume_against_job_description(resume, job_description, model="openai")
    print(gaps)

    updated_resume, diff_markdown = generate_updated_resume(resume, job_description, gaps)
    print(updated_resume)
    print(diff_markdown)

    cover_letter = generate_cover_letter(job_description, updated_resume, model="openai")
    return updated_resume, cover_letter

All previously-built functions composed into a single call — feed in an old resume and a target job description, get back a full gap analysis, tailored resume, tracked diff, and cover letter in one pass. Explicitly framed by the instructor as a legitimate small-scale startup idea, and noted as a natural next step toward wrapping this in an agentic system that could handle more of the job-application workflow autonomously.
