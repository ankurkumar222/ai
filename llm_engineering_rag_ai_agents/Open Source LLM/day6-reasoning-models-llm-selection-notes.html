Reasoning Models & A Framework for Choosing the Right LLM

A hands-on project: use DeepSeek's reasoning model to classify financial news, with its thinking shown out loud. Then a simple 5-step framework for picking the right model for any job, plus a tour of Hugging Face's leaderboards. Written to be used directly in real vendor/model calls.
Framing What Makes a "Reasoning Model" Different
▸
Think First: a reasoning model writes out its thinking before answering. Does that visible "thinking" text prove the model actually reasoned correctly — or could it just be more plausible-sounding text, same as any other LLM output? tap to reveal
It doesn't prove correctness by itself — the thinking text is generated the same way as any other LLM output: token by token, optimized to look like reasoning, not verified to BE correct reasoning. What it does give you is something to check: a step-by-step trace you (or a downstream validator) can actually inspect and catch an error in, instead of a bare answer you'd have to trust blindly. Visible thinking upgrades "trust me" to "here's my work, verify it" — which is a real improvement, but the verifying part is still on you, exactly like Section 6's CAPM check will show.

Goal: read a financial news headline and decide if it's positive, negative, or neutral — and show the thinking behind that decision, plus a topic tag. Model used: DeepSeek, an open-weight model anyone can download.

Big difference from a normal chat model: a reasoning model writes out its thinking, step by step, before giving the final answer. Like opening the brain and watching the thought process happen.

Architect's Lens

Think First: RAG proves its answer with citations you can click and check against a source. A reasoning model proves its answer with a "thinking" trace. Are these two transparency mechanisms actually equally trustworthy, or is one fundamentally weaker? tap to reveal

They're not equally strong. A citation points to an external, independently-checkable fact — you can open the source and verify it yourself, no trust in the model required. A "thinking" trace is still entirely the model's own generated text — plausible-sounding, but self-reported, with nothing external to check it against. Visible thinking is genuinely useful (it gives you something to audit instead of nothing), but it's a weaker transparency mechanism than citations, not an equivalent one. The strongest systems would use both: retrieval for facts, visible reasoning for how those facts were combined into a conclusion.

Data Loading Financial News from Hugging Face
▸
Think First: the dataset is deliberately kept small (~1.6MB, ~5,000 rows) so it fits a free GPU. Does keeping the DATASET small also mean the MODEL's understanding is limited to those 5,000 headlines — or is something else going on? tap to reveal
Something else entirely — this project isn't training the model on these 5,000 rows, it's running an already-trained model against them (inference, not fine-tuning). DeepSeek's actual knowledge comes from its massive original pretraining; these 5,000 rows are just the questions being asked of it, not lessons it's learning from. A small dataset here is small because it's a small TEST set, not because the model's understanding is limited to it.

Model Loading Downloading DeepSeek — Quantization and Pipeline Setup
▸
Think First: this project never fine-tunes DeepSeek — it only loads and runs it. So why does the SAME 4-bit quantization trick from the fine-tuning project show up again here, if there's no training happening? tap to reveal
Because quantization solves a memory problem that exists whether you're training or just running a model — a 1.5B-parameter model's weights take real memory to hold regardless of whether you're computing gradients against them or just reading through them for inference. The reason (fit a big model on a small/free GPU) is identical in both projects; only the workload on top of those loaded weights differs (backprop and updates vs. a single forward pass).
model = AutoModelForCausalLM.from_pretrained(
    model_id,                 # DeepSeek 1.5B parameters
    torch_dtype="auto",       # picks best precision (float16/32) for your hardware
    load_in_4bit=True,        # quantization — same memory-saving technique
                               # used in the fine-tuning project
    device_map="auto",        # auto-assigns GPU if available, else CPU
    trust_remote_code=True    # allows the model's custom code to run
)
tokenizer = AutoTokenizer.from_pretrained(model_id, trust_remote_code=True)
pipeline = pipeline("text-generation", model=model, tokenizer=tokenizer, ...)

Same 4-bit trick used in the earlier fine-tuning project shows up again here — just for running the model this time, not training it. Same reason both times: make a big model fit on a small (free) GPU.

Prompting Speaking DeepSeek's Native Format — Special Tokens for Reasoning
▸
Think First: the prompt ends with an unfinished tag, "<think>", with nothing after it. Why would leaving the prompt deliberately incomplete — instead of asking "please explain your reasoning" in plain English — be the more reliable way to trigger step-by-step thinking? tap to reveal
A plain-English request is a suggestion the model can follow loosely or ignore under other pressures in the prompt. An unfinished special token isn't a request — it's a structural cue the model was specifically trained to continue in one particular way (with reasoning text), because that's literally where "assistant turn, thinking mode" tokens appeared during its training. It's less "please think" and more "here's the exact spot where thinking goes — continue from here." That's why it's more reliable than asking nicely.
<IAM_START>user
[your question here]<IAM_END>
<IAM_START>assistant
<think>

That last <think> tag is the trick — it tells the model "show your reasoning before answering." Same idea as speaking a model's native chat format in the fine-tuning project, just aimed at unlocking visible thinking instead of just correct turns.

A few settings shape how the answer gets generated — see the sketch below for what each one does.

Rough Sketch

 prompt string sent to model:

 <IAM_START>user
 [question] <IAM_END>
 <IAM_START>assistant
 <think>        <---- trigger token: "show your reasoning first"

 settings that shape the answer:

  max_new_tokens=4000
     -> room for long reasoning (thinking can run on for a while)

  do_sample=True
     -> add some randomness, don't always pick the #1 likeliest word

  temperature  (0 ---------------------------------------- 2)
                deterministic,                         wild,
                factual, safe                       unpredictable

  top_p=0.9  (nucleus sampling)
     -> only pick from the smallest group of words whose combined
        chance adds up to 90% -- keeps it on-topic, still some variety
     -> too low = repetitive   |   no limit = rambling/incoherent

Architect's Lens

Think First: this trigger works because it exploits a structural pattern DeepSeek was trained on. If you swapped in a completely different model that was never trained with a "<think>" token at all, what would you expect to happen if you used this exact same trick? tap to reveal

Nothing useful — the model would likely just treat "<think>" as ordinary text (maybe even literally continuing "<think> about it..." as prose) rather than as a signal to enter a reasoning mode, because it was never trained to associate that specific token with that specific behavior. This is worth remembering as a general prompt-engineering principle, not DeepSeek trivia: a structural trigger only works for the model it was trained into. If a future Optimus prompt needs a model to "show its work," the first move is checking that specific model's documentation for its own trigger — not assuming this one transfers.

Parsing Separating "Thinking" from the Final Answer
▸
Think First: the split relies on finding literal "<think>" and end-of-think text inside the model's output string. What happens the day the model's reply doesn't contain those exact markers — say, it forgets to close the think tag, or phrases something slightly differently? tap to reveal
The split silently breaks — output.find() either returns "not found," or worse, finds a spurious match somewhere unintended, and the reasoning/answer separation comes out wrong or empty with no error raised. That's the core fragility of parsing by string search: it works exactly as long as the format holds, and breaks quietly (not loudly) the moment it doesn't. This is the same lesson as day7/day8's Pydantic sections wearing different clothes — raw text is not a contract, and a schema or structured-output approach fails loudly instead of silently.

The model's raw output is one messy blob — reasoning and final answer mixed together inside special tokens. Not usable as-is. A small function finds the <think> markers with simple string search and splits the text into two clean pieces.

Rough Sketch

 raw model output (one blob of text):
 "...<think> step 1... step 2... </think> Sentiment: Positive, Tag: Earnings"

                        |
                        |  output.find('<think>')
                        |  output.find(end-of-think marker)
                        v
        split into two pieces:

        +------------------+       +----------------------------+
        |  reasoning block |       |   final answer block        |
        |  (thinking text) |       |  (sentiment + tag, clean)   |
        +------------------+       +----------------------------+
              |                                  |
              v                                  v
          shown in UI                       shown in UI
       (transparency)                     (the actual result)

 method used: plain string search on hardcoded tokens
 more robust option: structured output / JSON schema / function
                      calling (less fragile if token format changes)

Architect's Lens

Think First: string-search parsing works fine in this demo. If you had to bet, would it survive a model VERSION UPGRADE unchanged — the same DeepSeek family, just a newer release? tap to reveal

Not a safe bet either way. Even within the same model family, a version upgrade can subtly change tokenization, default formatting, or how consistently the model closes its own tags — none of which show up as a documented breaking change, because the model provider isn't promising you a stable text contract, only a stable API surface. Raw model text was never an API contract, version to version any more than request to request. A schema-based approach (like the Pydantic pattern from the Vercel healthcare app) holds up across version bumps in a way string search on hardcoded tokens was never designed to.

Question worth sitting with

  • If this reasoning/answer-splitting logic were ever productionized for an Optimus tool, would you push for structured output (JSON schema, function calling) instead of string-searching for special tokens — and what would that trade off in terms of the reasoning trace's readability?
Validation Testing Reasoning on Math and Finance Problems
▸
Think First: the model gets the CAPM answer right — recalls the formula, does the substitution, reaches "undervalued." Does getting the right FINAL ANSWER prove the reasoning trace in between is actually correct, or could a wrong step and a right answer coexist? tap to reveal
They can absolutely coexist — a model could make two errors that cancel out, or get lucky on a comparison despite a wrong intermediate number, and still land on "undervalued." A correct final answer is necessary but not sufficient evidence that the reasoning was sound. The only way to actually know is to read the trace and check each step — the formula, the substitution, the arithmetic — independently of whether the conclusion happens to match. This is exactly why visible thinking matters: it gives you something to check beyond the bottom line.

Two extra tests, outside news sentiment, to check the model is really reasoning — not just pattern-matching:

  • Simple math: "5 apples, gave away 2+2, how many left?" → correctly worked through it and answered "1."
  • CAPM finance problem: given beta, risk-free rate, and market return, decide if a stock is under- or overvalued → model recalled the right formula, did the math, and got it right: undervalued. Full chain shown in the sketch below.

Rough Sketch

 CAPM validation chain (visible inside the reasoning trace):

  beta 1.2, risk-free 3%, market return 9%
             |
             v
  recall CAPM formula:  E(R) = Rf + beta * (Rm - Rf)
             |
             v
  substitute:  3% + 1.2 * (9% - 3%) = 3% + 7.2% = 10.2%  (CAPM-expected)
             |
             v
  compare to actual expected return: 10.5%
             |
             v
  10.5% > 10.2%  ==>  stock is UNDERVALUED

  a wrong FORMULA + a wrong SUBSTITUTION could still, by luck,
  cross the 10.5% line and land on "undervalued" -- the right
  answer alone never proves the middle steps were sound

Architect's Lens

Think First: your wealth/demat background lets you personally check this CAPM trace by eye. What happens to this whole verification approach the moment the finance concept is one you DON'T already know well enough to check by hand? tap to reveal

It breaks down — a visible reasoning trace is only as useful as your ability to actually verify it. You could check CAPM here because you already know the formula and could catch an error in it. For a formula or domain you don't know well, a fluent, confident-looking trace is just as persuasive whether it's right or wrong — you'd have no independent way to catch a subtle mistake. That's the real due-diligence question for any finance tool: not "does the reasoning trace exist," but "do you, or does some other check, actually have the domain knowledge to validate it" — because without that, visible thinking gives a false sense of security rather than real verification.

Comparison Reasoning Models vs. General Chat Models — Why It Matters for Classification
▸
Think First: "reasoning models keep the same structure every time" is stated here as a strength for pipelines. But is that reliability actually coming from the model being a REASONING model, or from something else entirely? tap to reveal
It's actually coming from something else — how the prompt was written and enforced, not from "reasoning" as a category. A reasoning model given a loose, unstructured prompt would drift in format just like a chat model would; a general chat model given a strict, well-designed prompt (or wrapped in structured output like day8's Pydantic pattern) can hold a consistent format too. Reasoning and structural consistency are two separate properties that happened to get demonstrated together in this project — worth not conflating "shows its thinking" with "always outputs a fixed format," since they don't automatically come as a package.

A regular chat model answers like a person talking ("I think this sounds negative because...") but its format shifts from request to request. A reasoning model, followed carefully, keeps the same delimited structure every time — which matters when code, not a human, is reading the output.

Rough Sketch

 General chat model:
   "I think this sounds negative because..."
   (free-form prose, format changes request to request)
   result: X breaks automated parsing once you scale to
           thousands of rows

 Reasoning model (with a good prompt):
   <think>...</think> Sentiment: X | Tag: Y
   (same structure, every single time)
   result: OK parses reliably, request 1 or request 10,000

 rule of thumb: one-off answer for a human to read -> either works
                pipeline reading 1,000s of rows automatically -> need
                the consistent, structured one
Framework A Five-Step Framework for Choosing the Right LLM
▸
Think First: step 2 asks "do you even need an LLM?" before any other model question. Think of a real Optimus request that arrived as "we need an AI/LLM solution for X" — is that framing itself already a warning sign, before you even get to step 3? tap to reveal
Often, yes — a request that names the SOLUTION ("we need an LLM") before establishing the actual NEED (classify these, retrieve that, summarize this) has usually skipped step 1 and step 2 entirely. It's the AI equivalent of a stakeholder saying "we need a bigger server" before anyone's confirmed the current one is actually the bottleneck. The framework's real value isn't steps 3-5 (model size, sourcing, scaling) — it's that steps 1-2 force the requester to justify needing an LLM at all before any model-selection conversation starts.
1. Define your needs
   - Core task: summarization? classification? search? generation?
   - Expected input/output, data privacy requirements, latency needs,
     time-to-market, build cost, inference cost

2. Choose the model TYPE
   - Not every problem needs an LLM at all — classification, NER,
     and retrieval can often be solved WITHOUT a generative LLM
   - LLM genuinely needed for: summarization, generation, translation,
     conversational chat, and REASONING (this project's use case)

3. Choose the right model SIZE
   - Small/medium (<50B params) vs. large/extra-large (>50B params)
   - Trade-offs: performance, inference cost, latency, knowledge depth,
     reasoning quality, environmental impact, deployment complexity
   - Small models can be boosted via fine-tuning OR RAG rather than
     simply defaulting to "bigger model"

4. Choose the SOURCING option
   - Build from scratch (rarely justified — GPT-3 cost ~$100M to train)
   - Open-source pretrained (Hugging Face) — low/no license cost,
     but higher deployment expertise cost (estimated 50-100% higher
     effective cost once expertise + GPU time are counted)
   - Proprietary via cloud API (OpenAI, AWS, etc.) — faster
     time-to-market, less data transparency, ongoing usage fees

5. Decide how the solution SCALES
   - Data residency requirements (some jurisdictions require local
     storage/processing)
   - Expected volume/traffic vs. API rate limits
   - Skills needed (prompt engineering through full model training)
   - End-to-end cost across build vs. RAG vs. fine-tune approaches
   - Operational capability: can you actually run and maintain this?

Rough Sketch

      task, I/O, privacy, latency, time-to-market, cost
             |
             v
 [2] CHOOSE MODEL TYPE  --- "do you even need an LLM?"
      classification/NER/retrieval? --> maybe NO LLM needed
      summarization/generation/translation/chat/reasoning? --> YES, LLM
             |
             v
 [3] CHOOSE MODEL SIZE
      small/medium (<50B)  <--- boost via fine-tune or RAG
      large/XL (>50B)      <--- more knowledge/reasoning, higher cost
             |
             v
 [4] CHOOSE SOURCING
      build from scratch (rare, ~$100M)
      open-source pretrained (low license cost, +50-100% deploy cost)
      proprietary cloud API (fast, less transparency, usage fees)
             |
             v
 [5] DECIDE HOW IT SCALES

      end-to-end cost, can you actually operate it?

Architect's Lens

Think First: step 4 says open-source deployment can run 50-100% MORE expensive in practice once expertise and GPU time are counted, despite "free" licensing. Given your AWS Day 5 experience with IAM/Docker/App Runner setup friction — does that number feel too high, too low, or about right? tap to reveal

Worth checking against your own lived experience rather than taking the number at face value. "Free and open source" only covers the license — every hour spent on IAM permissions, Docker configuration, App Runner setup, GPU provisioning, and ongoing maintenance is real engineering cost that a proprietary API call skips entirely. Whether that lands at 50%, 100%, or something else depends heavily on how much of that infrastructure work your team already has reusable versus building fresh each time — which is exactly the kind of number worth pressure-testing against your own team's actual deployment friction before citing it in a real build-vs-buy conversation.

▸
Think First: "open-source" and "free" get used almost interchangeably, but this table shows open-source deployment can cost 50-100% MORE in practice. What is the word "free" actually referring to here, if not the total cost? tap to reveal
"Free" refers only to the LICENSE — you don't pay to download or use the model weights. It says nothing about deployment cost: the GPU time, the integration expertise, the ongoing maintenance, the infrastructure to serve it reliably at scale. A proprietary API bundles all of that into one usage fee; open-source unbundles it into "free license + everything else you now have to build and staff yourself." Benchmarks Old vs. New Leaderboards — Benchmarks Get Beaten Fast
▸
Think First: if most frontier models now score above 80-85% on the OLD benchmarks, and a leaderboard still ranks models by those old scores, what would that ranking actually be measuring at this point — genuine ability, or something else? tap to reveal
At that point it's measuring noise, not ability — when everyone clusters near the ceiling, small score differences (83% vs 85%) stop reflecting real capability gaps and start reflecting benchmark quirks, evaluation methodology differences, or plain randomness. A saturated benchmark can't tell a genuinely better model from a slightly-differently-tuned one. That's exactly why Hugging Face had to retire the old set — not because the old benchmarks got "wrong," but because they stopped being able to discriminate at all once every model cleared the bar.

The old benchmarks got too easy. Within about 1.5 years, most models scored above 80–85% on all of them — so they stopped telling models apart. Hugging Face had to bring in much harder ones.

Architect's Lens

Think First: today's "hard" benchmarks (Humanity's Last Exam, best models ~35%) will likely saturate too, on the same ~1.5 year timeline. If you were designing an internal Optimus model-evaluation process, would you build it around specific benchmark NAMES, or something else entirely? tap to reveal

Something else — build the process around a re-verification HABIT, not a fixed benchmark list. Any benchmark named today has a documented shelf life of roughly 1-2 years before saturation makes it stop discriminating between models. A process that hardcodes "we evaluate against GPQA and MATH" will need updating on a schedule anyway, so the actual durable asset is the discipline: always check the benchmark's publication date, always re-verify scores close to the decision (not from memory of a leaderboard position from six months ago), and always expect today's "hard" test to be tomorrow's saturated one. Worth remembering for both vendor decisions and AI/ML interviews.

Practical Use Filtering Leaderboards by What Actually Matters to You
▸
Think First: the leaderboard lets you sort by MATH score for a finance tool, or GPQA for a research assistant — picking the benchmark that matches your use case. What's the risk of picking the model that TOPS your chosen benchmark, versus the model that scores well across several relevant ones? tap to reveal
Optimizing for a single benchmark risks picking a model that's been specifically tuned (deliberately or incidentally) to that one test's style of question, without broader competence you'll actually need in production — real user queries rarely look exactly like benchmark questions. A model that scores well across several related benchmarks (say, MATH AND general reasoning AND instruction-following) is a safer bet than the single highest MATH score, the same way you wouldn't hire based on one interview question alone.

You can filter the leaderboard by size, precision, and fine-tuned vs. pre-trained — so you sort by whatever score actually matters to you (MATH for a finance tool, GPQA for a research assistant). A separate performance leaderboard plots accuracy against speed, so you can see the trade-off directly. Domain leaderboards (coding, medical) exist too.

Architect's Lens

Think First: "pick the best point on the accuracy/latency/cost triangle for your SLA" sounds clean in theory. In practice, who at IDFC would actually know the real latency tolerance for a given use case — is that even a question the engineering team can answer alone? tap to reveal

Usually not alone — a quick eligibility check's real latency tolerance is as much a product/business decision as an engineering one (how long will a customer wait before abandoning the flow?), and an overnight batch job's tolerance depends on operational scheduling constraints outside engineering. The "best point on the triangle" framing is the right mental model, but applying it for real requires pulling in whoever owns the actual SLA or user experience for that specific use case — not just picking a number engineering finds comfortable. Worth treating model selection as a cross-functional input, not a purely technical one, the same way "how fast does this need to be" already is for any other fintech feature.

Wrap-up Project Recap
▸
Think First: this project covers two very different things under one title — a hands-on DeepSeek reasoning demo, and a general 5-step framework for picking any LLM. If you could only remember ONE of the two a year from now, which would still be useful, and why? tap to reveal
The 5-step framework ages much better. The DeepSeek specifics — its exact special tokens, its reported training cost, its benchmark scores — will be stale within a year or two, the same way this project's own Section 10 shows benchmarks going stale on a ~1.5 year cycle. The framework (define needs → do you even need an LLM → size → sourcing → scaling) is a way of THINKING that doesn't expire just because the specific models it's applied to change. The demo teaches the mechanics of one moment in time; the framework teaches a durable decision process — worth weighting your review time accordingly.
1. Reasoning models (DeepSeek) expose visible chain-of-thought,
   unlike typical general-purpose chat models
2. Load quantized model + tokenizer; build a text-generation pipeline
3. Speak the model's native chat-template format, including the
   explicit <think> trigger to unlock reasoning output
4. Parse the raw output into separate reasoning + answer sections
5. Validate reasoning on math and domain-specific (CAPM finance)
   problems — not just the target news-sentiment task
6. Five-step framework: define needs → choose model type → choose
   model size → choose sourcing → decide how it scales
7. "Do you even need an LLM?" is the cheapest, most important
   early filter in the whole framework
8. Benchmarks saturate fast — always check recency before trusting
   a leaderboard position
9. Model selection = optimizing a position on the accuracy/latency/
   cost frontier for YOUR constraint, not chasing the top score
10. Wrapped in a Gradio interface for interactive sentiment +
    reasoning + tag classification
