Reasoning Models & A Framework for Choosing the Right LLM

Notes from a hands-on project — using DeepSeek's reasoning model to classify financial news with transparent chain-of-thought explanations, followed by a structured five-step framework for picking the right model type, size, and sourcing option for a business use case, plus a tour of Hugging Face's leaderboards. Structured for a Senior Engineering Manager who will likely use the framework section directly in real vendor/model evaluation conversations.
Framing What Makes a "Reasoning Model" Different
▸

Project goal: classify financial news headlines as positive/negative/neutral with visible reasoning — not just a label, but the model's actual chain-of-thought explaining why it reached that conclusion, plus a topical tag. Model used: DeepSeek (open-weight, downloadable) — notable for reportedly costing ~$5–6M to train vs. GPT-4's reported ~$100M, while showing strong reasoning and instruction-following.

The differentiator versus a general-purpose chat model: a reasoning model exposes its internal "thinking" as text before producing a final answer — described as being able to "open the brain and see the train of thought," directly improving transparency and explainability.

Architect's Lens

Visible chain-of-thought is the single most production-relevant feature here — for any classification decision that has downstream consequences (risk flags, compliance triage, customer communications), being able to show why a model reached a conclusion is often as important as the conclusion itself, especially in an audited, regulated environment. This is the same transparency value proposition the RAG project delivered via citations — reasoning models deliver it via exposed thought process instead. Worth treating both as complementary transparency mechanisms, not competing ones.

Active Recall: What's the core structural difference between a reasoning model's output and a standard chat model's output for this task? tap to reveal
A reasoning model produces an explicit "thinking" section — its step-by-step internal reasoning as visible text — before generating the final structured answer (sentiment + tag). A standard general-purpose chat model tends to answer more conversationally and doesn't reliably separate or expose that reasoning process in a consistent, parseable format.
Data Loading Financial News from Hugging Face
▸

Dataset: ~5,000 financial news rows (id, main_domain/source like CNBC, title, description, created_at) — deliberately small (~1.6MB) so it runs comfortably on Colab's free-tier GPUs. Explored first via Hugging Face's Data Studio, including a natural-language "AI query" feature (e.g. "filter to CNBC news only") for quick exploratory filtering before writing any code.

Title and description are combined into one full_text field via a small mapping function — this combined text is what actually gets fed to the model, since a headline alone is often too thin a signal for reliable sentiment classification.

Active Recall: Why combine title and description into a single "full_text" field instead of feeding the title alone? tap to reveal
A headline alone often lacks enough context for reliable sentiment classification — combining it with the fuller description gives the model more signal to reason from, producing more accurate and better-justified sentiment judgments.
Model Loading Downloading DeepSeek — Quantization and Pipeline Setup
▸ 
model = AutoModelForCausalLM.from_pretrained(
    model_id,                 # DeepSeek 1.5B parameters
    torch_dtype="auto",       # picks best precision (float16/32) for your hardware
    load_in_4bit=True,        # quantization — same memory-saving technique
                               # used in the fine-tuning project
    device_map="auto",        # auto-assigns GPU if available, else CPU
    trust_remote_code=True    # allows the model's custom code to run
)
tokenizer = AutoTokenizer.from_pretrained(model_id, trust_remote_code=True)
pipeline = pipeline("text-generation", model=model, tokenizer=tokenizer, ...)

Same quantization technique (4-bit) as the earlier LoRA fine-tuning project reappears here — this time purely for inference, not training, but for the same reason: making a capable model runnable on a free-tier GPU.

Active Recall: Why is 4-bit quantization used here even though this project only does inference, not any training/fine-tuning? tap to reveal
To reduce the model's memory footprint so it fits and runs efficiently on limited hardware (a free-tier Colab GPU) — quantization saves memory regardless of whether you're doing inference or training, since it reduces how many bits are used to store each weight.
Prompting Speaking DeepSeek's Native Format — Special Tokens for Reasoning
▸ 
<IAM_START>user
[your question here]<IAM_END>
<IAM_START>assistant
<think>

The trailing <think> tag is the key mechanism — it explicitly cues the model to generate its internal reasoning before the final answer. This is the same "speak the model's native chat-template language" pattern seen with Gemma/DeepSeek formatting in the fine-tuning project, applied here specifically to unlock visible reasoning rather than just correct turn structure.

Generation parameters used: max_new_tokens=4000 (reasoning traces can be long), do_sample=True (adds controlled randomness instead of always picking the single highest-probability next token), temperature (0 = deterministic/factual, up to 2 = increasingly erratic), top_p=0.9 (nucleus sampling — sample only from the smallest set of tokens whose cumulative probability reaches 90%, keeping output on-topic while still allowing variety).

Architect's Lens

The explicit <think> token as a reasoning trigger is worth remembering as a concrete prompt-engineering lever, not model-specific trivia — many reasoning-capable models expose a similar mechanism (explicit or implicit) to separate deliberation from the final answer. If your multi-LLM bootcamp work or Optimus prompt templates ever need a model to "show its work" before answering, checking whether the target model has an equivalent trigger is the first thing to verify, since it directly affects both output quality and how much you need to parse afterward.

Active Recall: What does top_p=0.9 (nucleus sampling) actually restrict, and why does it help keep output "on topic"? tap to reveal
It restricts the model to sampling the next token only from the smallest set of candidate tokens whose combined probability reaches 90% — rather than considering every possible token or only the single most likely one. This keeps generation focused on plausible, contextually relevant words while still allowing some variety, avoiding both rigid repetition (top_p too low) and incoherent output (no restriction at all).
Parsing Separating "Thinking" from the Final Answer
▸

Raw model output interleaves the reasoning trace and the final answer inside special tokens — not directly usable in a UI. A small parsing function locates the <think> / end-of-think markers using string search (output.find(...)) and splits the text into two pieces: the reasoning block and the final answer block, so each can be displayed separately.

Architect's Lens

This is a direct, hands-on illustration of why structured/parseable output matters for anything beyond a demo — raw model text is not an API contract. Any production use of this pattern would want a more robust extraction than string search on hardcoded tokens (e.g. explicit structured-output formatting, or a schema the model is instructed to follow, similar to the Pydantic pattern from the Vercel course's healthcare app) — fragile string parsing on model-specific special tokens is a maintenance risk if the underlying model or its token format ever changes.

Validation Testing Reasoning on Math and Finance Problems
▸

Two validation tests beyond news sentiment, deliberately chosen to probe genuine multi-step reasoning rather than pattern-matching:

  • Simple arithmetic word problem ("5 apples, gave away 2+2, how many left?") — correctly reasoned through subtraction step-by-step and answered "1."
  • CAPM finance problem (beta 1.2, expected return 10.5%, risk-free rate 3%, market return 9% — is the stock under/overvalued?) — the model correctly recalled the Capital Asset Pricing Model formula, substituted the given numbers, computed the CAPM-expected return (~10.2%), compared it to the actual expected return (10.5%), and correctly concluded the stock is undervalued.

Architect's Lens

The CAPM test is the more interesting validation of the two — it required the model to recall a specific domain formula unprompted, correctly substitute given variables, and interpret the numeric comparison correctly, all visible in the reasoning trace. That's a genuinely useful capability check for any finance-adjacent internal tool: not "can it sound confident," but "can you watch it show its work and verify the formula and substitution were actually correct" — which is exactly the kind of due diligence a domain expert (you, given your wealth/demat background) would want before trusting such a model's output on a real financial calculation.

Active Recall: In the CAPM test, what specific values did the model need to correctly reason through to reach the right conclusion? tap to reveal
It needed to recall the CAPM formula itself, correctly substitute the given beta (1.2), risk-free rate (3%), and market return (9%) into that formula to compute the CAPM-expected return (~10.2%), and then correctly compare that to the stock's actual expected return (10.5%) to conclude the stock is undervalued (actual return exceeds what CAPM predicts for its risk level).
Comparison Reasoning Models vs. General Chat Models — Why It Matters for Classification
▸

Explicit contrast drawn: a general-purpose chat model might answer a sentiment question conversationally ("I think this sounds negative because...") but tends to struggle with consistently following a strict, structured output format (separate reasoning / sentiment / tag fields) across many requests. A reasoning model with strong instruction adherence reliably produces predictable, delimited output — essential when the output needs to be parsed programmatically at scale, not just read by a human.

Active Recall: Why does structured-output reliability matter more for a classification pipeline than for a one-off conversational answer? tap to reveal
Because a classification pipeline needs to programmatically parse the output (extract sentiment, tag, reasoning) across potentially thousands of requests reliably and consistently — a model that answers conversationally and inconsistently formats its output breaks automated parsing, whereas a one-off human-read answer doesn't need that structural consistency.
Framework A Five-Step Framework for Choosing the Right LLM
▸ 
1. Define your needs
   - Core task: summarization? classification? search? generation?
   - Expected input/output, data privacy requirements, latency needs,
     time-to-market, build cost, inference cost

2. Choose the model TYPE
   - Not every problem needs an LLM at all — classification, NER,
     and retrieval can often be solved WITHOUT a generative LLM
   - LLM genuinely needed for: summarization, generation, translation,
     conversational chat, and REASONING (this project's use case)

3. Choose the right model SIZE
   - Small/medium (<50B params) vs. large/extra-large (>50B params)
   - Trade-offs: performance, inference cost, latency, knowledge depth,
     reasoning quality, environmental impact, deployment complexity
   - Small models can be boosted via fine-tuning OR RAG rather than
     simply defaulting to "bigger model"

4. Choose the SOURCING option
   - Build from scratch (rarely justified — GPT-3 cost ~$100M to train)
   - Open-source pretrained (Hugging Face) — low/no license cost,
     but higher deployment expertise cost (estimated 50-100% higher
     effective cost once expertise + GPU time are counted)
   - Proprietary via cloud API (OpenAI, AWS, etc.) — faster
     time-to-market, less data transparency, ongoing usage fees

5. Decide how the solution SCALES
   - Data residency requirements (some jurisdictions require local
     storage/processing)
   - Expected volume/traffic vs. API rate limits
   - Skills needed (prompt engineering through full model training)
   - End-to-end cost across build vs. RAG vs. fine-tune approaches
   - Operational capability: can you actually run and maintain this?

Architect's Lens

This is the most directly reusable artifact in the whole project — a genuinely solid checklist for evaluating any proposed AI tool inside Optimus, structured almost identically to how you'd evaluate a build-vs-buy decision for any enterprise software component. Step 2 in particular ("do you even need an LLM?") is worth institutionalizing as the very first question in any Optimus intake process — it's the cheapest possible filter against over-engineering a classical classification or retrieval problem with an unnecessarily expensive generative model.

Questions worth sitting with

  • Does your current Optimus intake/prompt-template process already ask "does this actually need an LLM, or would a classical model / rules engine / simple retrieval solve it" as an explicit early gate — or does every request default straight to an LLM-based solution?
  • For step 4 (sourcing), the "50-100% higher effective cost" estimate for open-source deployment due to expertise overhead is a striking number — does that match your own intuition from the AWS Day 5 experience (IAM, Docker, App Runner setup friction) about how much real engineering effort sits underneath "it's free and open source"?
Active Recall: According to the framework, what should be the very first question asked before choosing between LLM options at all? tap to reveal
Whether the problem actually requires a generative LLM in the first place — many tasks like classification, named entity recognition, or simple retrieval can often be solved effectively (and much more cheaply) with classical machine learning models or simpler retrieval-based systems, without needing an LLM at all.

Benchmarks Old vs. New Leaderboards — Benchmarks Get Beaten Fast
▸

Notable finding: the "old" common benchmarks (DROP, HellaSwag, MMLU, ARC, TruthfulQA, WinoGrande, HumanEval, MT-Bench) went from being considered genuinely hard to being scored above 80-85% across the board by most models within about a year and a half — effectively saturated. This forced Hugging Face to introduce much harder new benchmarks.

New BenchmarkTests
Humanity's Last Exam2,500 extremely hard, hand-crafted questions — best models score only ~35%
GPQA (Google-Proof Q&A)PhD-level chemistry/biology/physics — designed to resist being solved via lookup
MuSRMulti-step soft reasoning over long text
BBH (Big-Bench Hard)Challenging tasks across language, math reasoning
IFEvalInstruction-following fidelity
MATHCompetition-level (not trivial) mathematics
AgentBench / WebArena / ToolBenchAgentic capability — tool use, multi-step task execution, memory
CO2 costEnvironmental/energy footprint of running the model

Architect's Lens

The "benchmarks get saturated within 1-2 years" pattern is itself the most important takeaway, more than any specific score — any model evaluation done today needs to be treated as a snapshot with a short shelf life. For real vendor/model selection decisions (relevant to your AI/ML job search conversations too), it's worth explicitly checking benchmark dates and re-verifying scores close to decision time rather than relying on remembered leaderboard positions from even six months prior.

Active Recall: Why did Hugging Face need to retire its original leaderboard benchmarks and introduce a new, harder set? tap to reveal
Because LLMs improved so quickly that most models were scoring above 80-85% on the original benchmarks within about a year and a half — the benchmarks became saturated and stopped meaningfully differentiating model quality, so a new set of substantially harder benchmarks (Humanity's Last Exam, GPQA, etc.) was introduced to restore meaningful comparison.
Practical Use Filtering Leaderboards by What Actually Matters to You
▸

The leaderboard UI supports filtering by parameter count, precision (4-bit vs. float16/bfloat16), and fine-tuned vs. pre-trained — letting you sort specifically on the benchmark relevant to your use case (e.g. sort by MATH score if building a finance/quant tool, by GPQA if building a scientific research assistant). A separate LLM Performance leaderboard plots accuracy against latency directly — visually surfacing the accuracy-vs-speed trade-off (e.g. Phi-3 shown as a strong accuracy/latency balance point; larger models like Qwen scoring higher but at higher latency and compute cost). Domain-specific leaderboards exist too (coding, medical) for even more targeted comparison.

Architect's Lens

The accuracy-vs-latency scatter plot is worth internalizing as a mental model even without looking at the live leaderboard: model selection is rarely "pick the highest score," it's "pick the best point on the accuracy/latency/cost frontier for your specific constraint." That framing maps directly onto latency-sensitive fintech APIs (a quick eligibility check needs different latency tolerance than an overnight batch reconciliation job) — the same model-selection logic, just with your own SLAs substituted for benchmark latency.

Wrap-up Project Recap
▸ 
1. Reasoning models (DeepSeek) expose visible chain-of-thought,
   unlike typical general-purpose chat models
2. Load quantized model + tokenizer; build a text-generation pipeline
3. Speak the model's native chat-template format, including the
   explicit <think> trigger to unlock reasoning output
4. Parse the raw output into separate reasoning + answer sections
5. Validate reasoning on math and domain-specific (CAPM finance)
   problems — not just the target news-sentiment task
6. Five-step framework: define needs → choose model type → choose
   model size → choose sourcing → decide how it scales
7. "Do you even need an LLM?" is the cheapest, most important
   early filter in the whole framework
8. Benchmarks saturate fast — always check recency before trusting
   a leaderboard position
9. Model selection = optimizing a position on the accuracy/latency/
   cost frontier for YOUR constraint, not chasing the top score
10. Wrapped in a Gradio interface for interactive sentiment +
    reasoning + tag classification
