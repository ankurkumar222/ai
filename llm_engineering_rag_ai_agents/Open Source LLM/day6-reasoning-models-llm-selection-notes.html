Reasoning Models & A Framework for Choosing the Right LLM

A hands-on project: use DeepSeek's reasoning model to classify financial news, with its thinking shown out loud. Then a simple 5-step framework for picking the right model for any job, plus a tour of Hugging Face's leaderboards. Written to be used directly in real vendor/model calls.
Framing What Makes a "Reasoning Model" Different
▸

Goal: read a financial news headline and decide if it's positive, negative, or neutral — and show the thinking behind that decision, plus a topic tag. Model used: DeepSeek, an open-weight model anyone can download.

Big difference from a normal chat model: a reasoning model writes out its thinking, step by step, before giving the final answer. Like opening the brain and watching the thought process happen.

Rough Sketch

 CHAT MODEL                              REASONING MODEL (DeepSeek)
 -----------                             ---------------------------
 headline+desc                           headline+desc
      |                                        |
      v                                        v
  [ LLM ]  (black box,                     [ LLM ]
   no visible work)                             |
      |                                         v
      v                                  +-----------------+
   answer                                | "thinking..."   |  <- you can
   (take it or                           | step 1, 2, 3... |     SEE this
    leave it)                            +-----------------+     part
                                                 |
                                                 v
                                          final answer
                                        (sentiment + tag)

 COST TO TRAIN (reported):
   GPT-4  ~$100,000,000
   DeepSeek ~$5,000,000 - $6,000,000   (cheap, still reasons well)

 WHY IT MATTERS: for risk flags, compliance, customer-facing
 decisions -- "why did the model say this?" matters as much as
 the answer itself. (Same transparency goal as RAG's citations,
 different mechanism: RAG shows sources, this shows thinking.)

Architect's Lens

Visible thinking is the most useful part of this whole project — in a regulated, audited environment, being able to show why is often as important as the answer itself. Think of this as a sibling to RAG's citations: RAG proves its answer with sources, reasoning models prove it with visible thought. Use both where you can.

Active Recall: What's the core structural difference between a reasoning model's output and a standard chat model's output for this task? tap to reveal
A reasoning model produces an explicit "thinking" section — its step-by-step internal reasoning as visible text — before generating the final structured answer (sentiment + tag). A standard general-purpose chat model tends to answer more conversationally and doesn't reliably separate or expose that reasoning process in a consistent, parseable format.
Data Loading Financial News from Hugging Face
▸

Dataset: ~5,000 rows of financial news (id, source like CNBC, title, description, date). Small on purpose (~1.6MB) so it runs fine on Colab's free GPUs.

First explored using Hugging Face's Data Studio — it even lets you type plain English like "filter to CNBC news only" instead of writing code.

Title alone is too thin a signal for sentiment. So title + description get merged into one full_text field before going to the model.

Active Recall: Why combine title and description into a single "full_text" field instead of feeding the title alone? tap to reveal
A headline alone often lacks enough context for reliable sentiment classification — combining it with the fuller description gives the model more signal to reason from, producing more accurate and better-justified sentiment judgments.

Active Recall: Why is 4-bit quantization used here even though this project only does inference, not any training/fine-tuning? tap to reveal
To reduce the model's memory footprint so it fits and runs efficiently on limited hardware (a free-tier Colab GPU) — quantization saves memory regardless of whether you're doing inference or training, since it reduces how many bits are used to store each weight.
Prompting Speaking DeepSeek's Native Format — Special Tokens for Reasoning
▸ 
<IAM_START>user
[your question here]<IAM_END>
<IAM_START>assistant
<think>

That last <think> tag is the trick — it tells the model "show your reasoning before answering." Same idea as speaking a model's native chat format in the fine-tuning project, just aimed at unlocking visible thinking instead of just correct turns.

A few settings shape how the answer gets generated — see the sketch below for what each one does.

Rough Sketch

 prompt string sent to model:

 <IAM_START>user
 [question] <IAM_END>
 <IAM_START>assistant
 <think>        <---- trigger token: "show your reasoning first"

 settings that shape the answer:

  max_new_tokens=4000
     -> room for long reasoning (thinking can run on for a while)

  do_sample=True
     -> add some randomness, don't always pick the #1 likeliest word

  temperature  (0 ---------------------------------------- 2)
                deterministic,                         wild,
                factual, safe                       unpredictable

  top_p=0.9  (nucleus sampling)
     -> only pick from the smallest group of words whose combined
        chance adds up to 90% -- keeps it on-topic, still some variety
     -> too low = repetitive   |   no limit = rambling/incoherent

Architect's Lens

Remember the <think> trigger as a general prompt-engineering tool, not DeepSeek trivia — most reasoning models have something similar. If a future Optimus prompt needs a model to "show its work," check for this trigger first. It changes both output quality and how much parsing you'll need to do later.

Active Recall: What does top_p=0.9 (nucleus sampling) actually restrict, and why does it help keep output "on topic"? tap to reveal
It restricts the model to sampling the next token only from the smallest set of candidate tokens whose combined probability reaches 90% — rather than considering every possible token or only the single most likely one. This keeps generation focused on plausible, contextually relevant words while still allowing some variety, avoiding both rigid repetition (top_p too low) and incoherent output (no restriction at all).
Parsing Separating "Thinking" from the Final Answer
▸

The model's raw output is one messy blob — reasoning and final answer mixed together inside special tokens. Not usable as-is. A small function finds the <think> markers with simple string search and splits the text into two clean pieces.

Rough Sketch

 raw model output (one blob of text):
 "...<think> step 1... step 2... </think> Sentiment: Positive, Tag: Earnings"

                        |
                        |  output.find('<think>')
                        |  output.find(end-of-think marker)
                        v
        split into two pieces:

        +------------------+       +----------------------------+
        |  reasoning block |       |   final answer block        |
        |  (thinking text) |       |  (sentiment + tag, clean)   |
        +------------------+       +----------------------------+
              |                                  |
              v                                  v
          shown in UI                       shown in UI
       (transparency)                     (the actual result)

 method used: plain string search on hardcoded tokens
 more robust option: structured output / JSON schema / function
                      calling (less fragile if token format changes)

Architect's Lens

Good hands-on proof that raw model text is not an API contract. Fine for a demo, risky for production — string search on hardcoded tokens breaks if the model or its token format changes. A schema-based approach (like the Pydantic pattern from the Vercel healthcare app) holds up better.

Question worth sitting with

  • If this reasoning/answer-splitting logic were ever productionized for an Optimus tool, would you push for structured output (JSON schema, function calling) instead of string-searching for special tokens — and what would that trade off in terms of the reasoning trace's readability?
Validation Testing Reasoning on Math and Finance Problems
▸

Two extra tests, outside news sentiment, to check the model is really reasoning — not just pattern-matching:

  • Simple math: "5 apples, gave away 2+2, how many left?" → correctly worked through it and answered "1."
  • CAPM finance problem: given beta, risk-free rate, and market return, decide if a stock is under- or overvalued → model recalled the right formula, did the math, and got it right: undervalued. Full chain shown in the sketch below.

Rough Sketch

 CAPM validation chain (visible inside the reasoning trace):

  beta 1.2, risk-free 3%, market return 9%
             |
             v
  recall CAPM formula:  E(R) = Rf + beta * (Rm - Rf)
             |
             v
  substitute:  3% + 1.2 * (9% - 3%) = 3% + 7.2% = 10.2%  (CAPM-expected)
             |
             v
  compare to actual expected return: 10.5%
             |
             v
  10.5% > 10.2%  ==>  stock is UNDERVALUED

Architect's Lens

CAPM is the more interesting test — the model had to recall a real finance formula unprompted, plug in the right numbers, and interpret the result. Not "does it sound confident," but "can you watch its work and check the formula and math were actually right." That's the real due-diligence question for any finance tool, and your wealth/demat background is exactly the lens for checking it.

Active Recall: In the CAPM test, what specific values did the model need to correctly reason through to reach the right conclusion? tap to reveal
It needed to recall the CAPM formula itself, correctly substitute the given beta (1.2), risk-free rate (3%), and market return (9%) into that formula to compute the CAPM-expected return (~10.2%), and then correctly compare that to the stock's actual expected return (10.5%) to conclude the stock is undervalued (actual return exceeds what CAPM predicts for its risk level).
Comparison Reasoning Models vs. General Chat Models — Why It Matters for Classification
▸

A regular chat model answers like a person talking ("I think this sounds negative because...") but its format shifts from request to request. A reasoning model, followed carefully, keeps the same delimited structure every time — which matters when code, not a human, is reading the output.

Rough Sketch

 General chat model:
   "I think this sounds negative because..."
   (free-form prose, format changes request to request)
   result: X breaks automated parsing once you scale to
           thousands of rows

 Reasoning model (with a good prompt):
   <think>...</think> Sentiment: X | Tag: Y
   (same structure, every single time)
   result: OK parses reliably, request 1 or request 10,000

 rule of thumb: one-off answer for a human to read -> either works
                pipeline reading 1,000s of rows automatically -> need
                the consistent, structured one
Active Recall: Why does structured-output reliability matter more for a classification pipeline than for a one-off conversational answer? tap to reveal
Because a classification pipeline needs to programmatically parse the output (extract sentiment, tag, reasoning) across potentially thousands of requests reliably and consistently — a model that answers conversationally and inconsistently formats its output breaks automated parsing, whereas a one-off human-read answer doesn't need that structural consistency.
Framework A Five-Step Framework for Choosing the Right LLM
▸ 
1. Define your needs
   - Core task: summarization? classification? search? generation?
   - Expected input/output, data privacy requirements, latency needs,
     time-to-market, build cost, inference cost

2. Choose the model TYPE
   - Not every problem needs an LLM at all — classification, NER,
     and retrieval can often be solved WITHOUT a generative LLM
   - LLM genuinely needed for: summarization, generation, translation,
     conversational chat, and REASONING (this project's use case)

3. Choose the right model SIZE
   - Small/medium (<50B params) vs. large/extra-large (>50B params)
   - Trade-offs: performance, inference cost, latency, knowledge depth,
     reasoning quality, environmental impact, deployment complexity
   - Small models can be boosted via fine-tuning OR RAG rather than
     simply defaulting to "bigger model"

4. Choose the SOURCING option
   - Build from scratch (rarely justified — GPT-3 cost ~$100M to train)
   - Open-source pretrained (Hugging Face) — low/no license cost,
     but higher deployment expertise cost (estimated 50-100% higher
     effective cost once expertise + GPU time are counted)
   - Proprietary via cloud API (OpenAI, AWS, etc.) — faster
     time-to-market, less data transparency, ongoing usage fees

5. Decide how the solution SCALES
   - Data residency requirements (some jurisdictions require local
     storage/processing)
   - Expected volume/traffic vs. API rate limits
   - Skills needed (prompt engineering through full model training)
   - End-to-end cost across build vs. RAG vs. fine-tune approaches
   - Operational capability: can you actually run and maintain this?

Rough Sketch

 [1] DEFINE NEEDS
      task, I/O, privacy, latency, time-to-market, cost
             |
             v
 [2] CHOOSE MODEL TYPE  --- "do you even need an LLM?"
      classification/NER/retrieval? --> maybe NO LLM needed
      summarization/generation/translation/chat/reasoning? --> YES, LLM
             |
             v
 [3] CHOOSE MODEL SIZE
      small/medium (<50B)  <--- boost via fine-tune or RAG
      large/XL (>50B)      <--- more knowledge/reasoning, higher cost
             |
             v
 [4] CHOOSE SOURCING
      build from scratch (rare, ~$100M)
      open-source pretrained (low license cost, +50-100% deploy cost)
      proprietary cloud API (fast, less transparency, usage fees)
             |
             v
 [5] DECIDE HOW IT SCALES
      data residency, volume vs. rate limits, skills needed,
      end-to-end cost, can you actually operate it?

Architect's Lens

The single most reusable thing in this whole project — a solid checklist for any proposed AI tool inside Optimus, basically a build-vs-buy checklist adapted for AI. Step 2 ("do you even need an LLM?") deserves to be the very first question in Optimus intake — the cheapest filter against overbuilding a simple classification problem with an expensive generative model.

  • For step 4 (sourcing), the "50-100% higher effective cost" estimate for open-source deployment due to expertise overhead is a striking number — does that match your own intuition from the AWS Day 5 experience (IAM, Docker, App Runner setup friction) about how much real engineering effort sits underneath "it's free and open source"?
Active Recall: According to the framework, what should be the very first question asked before choosing between LLM options at all? tap to reveal
Whether the problem actually requires a generative LLM in the first place — many tasks like classification, named entity recognition, or simple retrieval can often be solved effectively (and much more cheaply) with classical machine learning models or simpler retrieval-based systems, without needing an LLM at all.

Benchmarks Old vs. New Leaderboards — Benchmarks Get Beaten Fast
▸

The old benchmarks got too easy. Within about 1.5 years, most models scored above 80–85% on all of them — so they stopped telling models apart. Hugging Face had to bring in much harder ones.

New BenchmarkTests
Humanity's Last Exam2,500 extremely hard, hand-crafted questions — best models score only ~35%
GPQA (Google-Proof Q&A)PhD-level chemistry/biology/physics — designed to resist being solved via lookup
MuSRMulti-step soft reasoning over long text
BBH (Big-Bench Hard)Challenging tasks across language, math reasoning
IFEvalInstruction-following fidelity
MATHCompetition-level (not trivial) mathematics
AgentBench / WebArena / ToolBenchAgentic capability — tool use, multi-step task execution, memory
CO2 costEnvironmental/energy footprint of running the model

Architect's Lens

The real lesson isn't any one score — it's that benchmarks go stale within 1-2 years. Treat any model evaluation as a snapshot with a short shelf life. For real vendor decisions (and your AI/ML interviews), always check the benchmark date and re-verify scores close to decision time.

Active Recall: Why did Hugging Face need to retire its original leaderboard benchmarks and introduce a new, harder set? tap to reveal
Because LLMs improved so quickly that most models were scoring above 80-85% on the original benchmarks within about a year and a half — the benchmarks became saturated and stopped meaningfully differentiating model quality, so a new set of substantially harder benchmarks (Humanity's Last Exam, GPQA, etc.) was introduced to restore meaningful comparison.

Architect's Lens

Worth internalizing even without the live leaderboard open: pick the best point on the accuracy/latency/cost triangle for your constraint, not the highest score. Maps directly to fintech APIs — a quick eligibility check tolerates less latency than an overnight batch job. Same logic, your own SLAs instead of benchmark latency.

Wrap-up Project Recap
▸ 
1. Reasoning models (DeepSeek) expose visible chain-of-thought,
   unlike typical general-purpose chat models
2. Load quantized model + tokenizer; build a text-generation pipeline
3. Speak the model's native chat-template format, including the
   explicit <think> trigger to unlock reasoning output
4. Parse the raw output into separate reasoning + answer sections
5. Validate reasoning on math and domain-specific (CAPM finance)
   problems — not just the target news-sentiment task
6. Five-step framework: define needs → choose model type → choose
   model size → choose sourcing → decide how it scales
7. "Do you even need an LLM?" is the cheapest, most important
   early filter in the whole framework
8. Benchmarks saturate fast — always check recency before trusting
   a leaderboard position
9. Model selection = optimizing a position on the accuracy/latency/
   cost frontier for YOUR constraint, not chasing the top score
10. Wrapped in a Gradio interface for interactive sentiment +
    reasoning + tag classification
