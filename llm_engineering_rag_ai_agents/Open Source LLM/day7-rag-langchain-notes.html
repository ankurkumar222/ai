Architects Lab · RAG & LangChain Project

Retrieval-Augmented Generation with LangChain: "Ask 11 Madison Park"

A hands-on project: make an LLM answer questions using a restaurant's own website data — not just what it learned in training. Built with LangChain, OpenAI embeddings, ChromaDB, and a Gradio front end that shows its sources.
Framing What RAG Actually Is — Retrieve, Augment, Generate
▸
Think First: RAG never touches the model's weights — it only changes the prompt. So does RAG make a model "smarter," or just "better informed"? Is a small model with great retrieval always better than a big model with none? tap to reveal
RAG improves what a model KNOWS, not how well it THINKS. Retrieval supplies facts; reasoning quality still comes entirely from the underlying LLM. A weak model with perfect retrieval can still reason badly over correct facts (miscalculate, misinterpret, contradict itself). A strong model with bad retrieval will reason brilliantly over the wrong facts. Neither fixes the other's job — that's exactly why the CAPM-style validation-of-reasoning work (studied separately) and RAG's retrieval-quality work are two different disciplines, not one.

Ask an LLM directly, and it only knows what it learned in training — old, generic, or nothing about this one restaurant. RAG fixes that by feeding it the restaurant's own live data at question time. No retraining needed.

Rough Sketch — RAG in one picture

 User: "What kind of food does 11 Madison Park serve?"
                    |
                    v
 R - RETRIEVE  ---------------------------------------------
     search a vector database made of the restaurant's OWN
     data --> pull out the chunks that match the question
                    |
                    v
 A - AUGMENT  ----------------------------------------------
     question  +  retrieved chunks  --->  ONE combined prompt
                    |
                    v
 G - GENERATE  ---------------------------------------------
     send that combined prompt to the LLM
                    |
                    v
 Answer -- grounded in the RESTAURANT'S real data, not just
           whatever the model happened to learn during training

 KEY POINT: model weights are never touched. Only the prompt
            changes. Update the database, answers update too.
Comparison RAG vs. Fine-Tuning — When to Reach for Which
▸
Think First: If you could bolt fine-tuning AND RAG onto the same production system, what job would each one actually be doing — and when would using both together be genuinely additive vs. just redundant? tap to reveal
RAG's job: supply current, citable FACTS at request time. Fine-tuning's job: change HOW the model behaves — tone, format discipline, domain reasoning style — baked in permanently. Combining is additive when you need both: e.g. an IDFC bot that must always answer in a compliance-safe tone and structure (fine-tune) while pulling live, correct policy numbers (RAG). Combining is redundant if the actual problem is just "the model doesn't know current facts" — fine-tuning alone won't fix staleness, since retraining every time a policy changes defeats RAG's entire cost advantage.

Architect's Lens

Think First: this table treats fine-tuning and RAG as opposite tools for opposite jobs. Is there a real Optimus scenario where reaching for RAG would actually be the WRONG call, even though the information genuinely changes often? tap to reveal

Yes — when "changes often" is really "phrases itself differently every time" rather than "facts change." If the underlying facts are stable but the FORMAT or TONE the answer must follow is strict and non-negotiable (e.g. a legally-reviewed disclaimer wording that must never drift), RAG alone won't guarantee that discipline — the LLM still has freedom in how it stitches retrieved text into prose. That's a case for fine-tuning the output behavior, sometimes on top of RAG rather than instead of it. Same lesson as the separate LoRA project: fine-tuning is an expensive experiment with real failure risk, so reserve it for cases where behavior/format control is the actual requirement — not as a reflex whenever "often" appears in a sentence.

Tooling LangChain 101 — Why Use a Framework At All?
▸
Think First: LangChain hides a lot of manual wiring behind reusable chains. When a chain gives a bad answer in production, where does that convenience start working against you instead of for you? tap to reveal
The moment something breaks. A chain that "just works" hides which specific step failed — was it retrieval (wrong chunks found), the prompt assembly (context stuffed badly), or the LLM call itself (right context, bad generation)? The same abstraction that saves you from hand-wiring these steps also removes your visibility into them by default. The fix isn't avoiding frameworks — it's insisting on step-by-step tracing/logging (as section 7's isolated retrieval test does) so the black box stays debuggable, not just convenient.

Plain LLM use is one prompt, one reply. LangChain lets you chain steps together and reuse common building blocks instead of hand-wiring everything yourself.

Rough Sketch

 WITHOUT a framework:            WITH LangChain:
 one prompt --> one reply        search -> summarize -> translate
 (build every piece yourself)    (chained steps, reusable pieces)

 LangChain's building blocks:
   [ prompts ]  [ memory ]  [ tools/plugins ]  [ agents ]  [ retrieval/RAG ]
                                (calc, code,    (LLM picks    <- this
                                 search)         which tool)     project

Architect's Lens

Think First: an "opinionated framework" like LangChain bundles someone else's assumptions about how a RAG pipeline should be built. If your use case doesn't fit those assumptions, would you fight the framework to bend it — or drop back to raw API calls? Where's that line? tap to reveal

LangChain plays the same role Next.js played for the Vercel course — an opinionated framework on top of raw API calls, bundling common patterns so you don't build them by hand. That's a genuine speed win when your use case matches its assumptions (a standard retriever + chain + LLM shape, like this project). The line to drop back to raw calls is when you find yourself fighting the framework's defaults more than using them — configuring around a chain type instead of just writing the three lines of logic yourself. Know what's underneath before deciding which side of that line you're on.

Setup Loading the Source Document
▸
Think First: TextLoader reads the whole file as ONE document before anything is split. Why does that ORDER matter — could you embed the whole document first and split it into pieces later instead? tap to reveal
Order matters for a structural reason, not just convenience. An embedding compresses a chunk of text into ONE vector representing its overall meaning. Embed the entire document as one blob, and the menu, chef bio, and partnership info all get blended into a single averaged vector — which represents none of them well. Splitting BEFORE embedding is what lets each chunk's vector stay sharply about one topic, which is the entire reason retrieval can tell "menu questions" apart from "dress code questions" later. Embed-then-split isn't just unusual — it defeats the purpose.

Data: one scraped text file of 11 Madison Park's website (menu, contact info, chef bio, partnerships). Loaded whole with LangChain's TextLoader.

Rough Sketch

 11madisonpark.com  --(scrape)-->  one .txt file
                                          |
                                          v
                              TextLoader(file, encoding="utf-8")
                                          |
                                          v
                          ONE big document object
                          (menu + contact + chef bio + partnerships
                           all still stuck together, not split yet)

 Windows note: needs Microsoft Visual C++ 14+ installed,
               or LangChain won't install/run correctly
Chunking Splitting the Document — Chunk Size and Overlap
▸
Think First: chunk_size and overlap were tuned for a casual restaurant website. If you applied this same 1000/150 setting to IDFC's compliance policy documents instead, would that be a safe default — or does legal/regulated text need a fundamentally different chunking approach? tap to reveal
Almost certainly not safe as-is. A restaurant's ideas are short and independent — cutting mid-sentence loses a little color, not much else. A compliance clause cut mid-condition ("...eligible for the exemption UNLESS [cut here] the transaction exceeds ₹X") can flip the legal meaning of the retrieved chunk, and the model may confidently answer from the incomplete half. Regulated text usually wants chunking aligned to structural boundaries (clause, section, sub-section) rather than a fixed character count, plus enough overlap to guarantee no single condition ever gets orphaned from its clause. This is exactly the kind of default a fintech deployment can't just copy from a demo project.

A big document is hard to search well. Cut it into small chunks first — easier to store and find precisely. Uses LangChain's RecursiveCharacterTextSplitter.

Rough Sketch

 ONE big document
        |
        v  RecursiveCharacterTextSplitter(
        |     chunk_size=1000,    <- max characters per chunk
        |     chunk_overlap=150)  <- shared chars between chunks,
        v                            keeps context across the cut
 [chunk1][chunk2][chunk3]...[chunk38]     --> 38 chunks total
   each chunk also carries METADATA -> source file name
                                        (this = later citations)

 WHY OVERLAP?  zero overlap:
   "...the chef trained    |   in Switzerland before..."
                          CUT HERE -- sentence broken, meaning lost

   150-char overlap: a bit of text repeats on both sides of the
   cut, so no idea gets sliced clean in half

 EXPERIMENT RESULTS:
   chunk_size 1000 -> 38 chunks
   chunk_size  500 -> 79 chunks   (roughly double)
   overlap = 0     -> chunk count barely changes,
                       but boundary context gets WORSE

Risk Flag — Chunk Boundaries Can Cut Sentences in Half

Zero overlap means a sentence can get sliced right at the boundary, losing meaning. Overlap exists to fix exactly that.

Architect's Lens

Think First: "pick a sane default, then tune against real results" sounds obvious. What would actually tell you your chunk_size is wrong, if the demo's answers already look fine? tap to reveal

A demo "looking fine" is the trap — a handful of easy test questions can pass even with a badly tuned chunk size, because the answer to "what menus are offered" doesn't need precise boundaries. The real signal shows up on edge-case questions that straddle a chunk boundary, or questions needing two related facts that got split into different chunks. Chunk size/overlap is a real trade-off, not a throwaway setting: too big wastes context and pulls in noisy text, too small chops up ideas and hurts retrieval. Treat it like any tunable system parameter — cache TTL, batch size — and tune it against deliberately hard queries, not the easy ones that happen to work either way.

Embeddings Turning Text Into Vectors — And Storing Them in ChromaDB
▸
Think First: "king" sits near "queen" because they're close in MEANING. If your users type Hindi or Hinglish questions but every source document is in English, does semantic closeness still hold across languages — or does retrieval quietly fail? tap to reveal
It depends entirely on whether the embedding model was trained on multilingual data. Some embedding models do place semantically equivalent phrases from different languages reasonably close together — but "reasonably close" is weaker than same-language matching, and quality varies a lot by language pair and phrasing style (formal Hindi vs. casual Hinglish). This isn't something to assume — it's something to actually test with real Hinglish queries against your English docs before trusting it in an India-facing product. A silent, subtle retrieval failure (slightly-off chunks, not zero chunks) is far more dangerous than an obvious one, because the model will still answer fluently from whatever it got.

An embedding turns text into a list of numbers that captures its meaning. Similar meaning → numbers land close together.

Rough Sketch

 EASY EXAMPLE (3 imaginary axes: gender, age, "royalty"):

              royalty
                 |    king          queen
                 |      *             *
                 |         prince   princess
                 |            *      *
        ---------+------------------------- gender
                 |   boy         girl
                 |    *           *
                 |  man          woman
                 |   *             *
                age

    "king" is near "queen" and near "prince" -- because they
    are close in MEANING, not because the letters match

 REAL PROJECT: same idea, but 1,536 numbers per chunk (OpenAI
 embeddings) instead of 3 -- too many to draw, same principle

    type "Italy"  --> nearby words: France, Rome, Venice, Spain
    (2D/3D picture squashed down from 1,536 dimensions)

 STORING IT:
   Chroma.from_documents(chunks, OpenAIEmbeddings())
        |
        v
   for each of the 38 chunks, ChromaDB stores THREE things:
     1. the embedding vector (1,536 numbers -- the "meaning")
     2. the original chunk text (human-readable)
     3. the metadata (which source file it came from)

Architect's Lens

Think First: retrieval just returned the wrong chunks for a real question. Given only "bad chunking" and "bad embedding match" as the two usual suspects, how would you actually tell which one it was, without guessing? tap to reveal

Look at what came back, not just that it was wrong. If the retrieved chunks are on a completely different topic than the query, that usually points to an embedding/query-phrasing mismatch — the question's wording landed far from the right chunks in vector space. If the retrieved chunks are on the RIGHT topic but missing the specific detail asked about, that points to a chunking problem — the right idea got split away from the fact that answers the question. This embedding-space idea is the whole engine retrieval runs on, so diagnosing a failure always starts by asking which of these two things actually happened, not by re-tuning both at once.

Testing Verifying Retrieval Before Building the Full Chain
▸
Think First: if similarity_search returns confident, plausible-looking chunks that are actually subtly off-topic — not obviously wrong, just slightly off — would a quick manual spot-check like the one in this section even catch that? tap to reveal
Probably not. Eyeballing 3-5 test questions catches obvious misses (wrong topic entirely) but not "confidently wrong" retrieval — chunks that are related enough to look right at a glance but aren't actually the best match. That needs something more rigorous: a labeled test set of queries with their expected correct chunks, and a real precision/recall@k metric computed against it — not just a human reading the output and nodding. Manual spot-checks are a fine first pass, exactly like this section's demo, but they're not a substitute for a measured retrieval-quality benchmark before anything goes to production — the same QA discipline your fintech background would demand of any other data pipeline.

Before building the full chain, test retrieval alone first — "can we find the right info?" is a different question from "can we write a good answer from it?" Test one thing at a time.

Rough Sketch

 vector_store.similarity_search("what menus are offered?", k=3)
                    |
                    v
       does the top-3 come back menu-related?  YES -- retrieval works

 more test questions tried:
   "Who is Daniel Humm?"
   "Is there a dress code?"
   "Tell me about the partnership with Magic Farms"

 k = how many chunks come back:
   k=1 -----> * (just the single best match)
   k=2 -----> * *
   k=5 -----> * * * * *   (more context, but more noise too)

 WHY TEST THIS SEPARATELY?
   bad final answer could mean:
     (a) retrieval found the WRONG chunks    -> fix chunking/k/query
     (b) retrieval found the RIGHT chunks,
         but LLM wrote a bad answer          -> fix the prompt/LLM
   testing retrieval alone tells you which one broke

Architect's Lens

Think First: testing retrieval alone, before generation, is good discipline here with 38 chunks and a handful of test questions. Does that same isolated-testing approach still scale once you have thousands of chunks and can't manually eyeball every result? tap to reveal

Manually checking "does the top-3 look right" works at 38 chunks and stops working almost immediately after that — nobody eyeballs a thousand test queries. The isolated-testing PRINCIPLE still holds (retrieval and generation are still two separate things that can each fail), but the METHOD has to change: from "look at it and judge" to "score it automatically" — a labeled query set with expected chunks, measured precision/recall@k, run on a schedule. Same discipline as testing a database query alone before wiring it into an app, just industrialized instead of manual.

Chain Assembling the Full RAG Chain — RetrievalQAWithSourcesChain
▸
Think First: the "stuff" chain works today because 3 chunks fit the context window. The day your document set outgrows that, what would you actually SEE go wrong in production — a clean error, a crash, or something quieter and more dangerous? tap to reveal
Often something quieter. Depending on the client library and model, context overflow can raise a clear token-limit error — the "safe" failure — but it can also silently truncate the stuffed context, meaning the model answers fluently and confidently from an incomplete set of chunks, with no error at all. That silent case is the dangerous one: the answer looks exactly as trustworthy as a correct one. Worth deliberately testing at and beyond the context limit before trusting this pattern at any real scale, rather than assuming a clean failure mode.
retriever = vector_store.as_retriever(search_kwargs={"k": 3})
llm = OpenAI(temperature=0)

chain = RetrievalQAWithSourcesChain.from_chain_type(
    llm=llm, chain_type="stuff", retriever=retriever
)

result = chain.invoke(query)

 chain_type="stuff"
    -----------------------------------------------

    LIMIT: only works if chunks + question fit inside

    |

 TEMPERATURE EXPERIMENT:
   temperature=0    -> same facts, plain/consistent wording
   temperature=1.3  -> SAME facts, different wording/style
   conclusion: temperature changes HOW it's said,
               not WHETHER it's grounded (retrieval
               supplies the facts either way)

Architect's Lens

Think First: if this exact "stuff" pattern had to grow from a 38-chunk restaurant site to a 10,000-document IDFC policy library tomorrow, what's the FIRST thing that would need to change — the chain type, the chunk strategy, or something upstream of both? tap to reveal

The chain type is the obvious answer but not necessarily the first bottleneck — before touching "stuff" vs. map-reduce/refine, retrieval itself (k=3, plain similarity search) would likely need upgrading first, since a 10,000-document corpus makes top-3-by-similarity far more likely to miss the genuinely relevant chunk among near-duplicates. Fix retrieval precision first (better k tuning, maybe re-ranking), THEN worry about whether "stuff" still fits the context window with the right chunks found. Changing the chain type without fixing retrieval just stuffs more of the wrong context into the prompt, faster.

Interface Gradio Front End — Questions, Citations, and Polish
▸
Think First: a citation tells the user WHICH document an answer came from. It does not tell them whether that document is still accurate. What's missing from a "trustworthy" RAG answer if the cited source itself is stale? tap to reveal
Freshness. A citation creates a feeling of confidence ("it's grounded, it's sourced!") even when it's grounded in an outdated document. RAG only ever guarantees the answer matches what's IN the database — not that the database is current. A genuinely trustworthy setup would surface the source document's last-updated date alongside the citation, and have a real process for re-scraping/re-indexing when the underlying source changes — otherwise "cited" quietly gets mistaken for "correct," which is a dangerous gap for anything customer-facing or compliance-adjacent.

Last layer: wrap the chain in a Gradio interface, so a normal person can use it, not just code.

Architect's Lens

Think First: showing a citation is one thing. Would a regulator, auditor, or compliance reviewer actually accept "the UI displayed a source link" as proof of where an answer came from — or does auditable mean something stricter than visible? tap to reveal

Visible-in-the-UI and auditable are not the same bar. A citation shown to a user is a trust signal for THEM in the moment — it doesn't by itself create a durable record. A real audit trail needs the retrieved chunk, the exact prompt sent, the model's response, and the citation all logged together with a timestamp, so a reviewer can reconstruct "why did the system say this" months later, not just see a source name that flashed on screen. For any regulated or customer-facing Optimus tool, visible citations are the right first step, but the non-negotiable requirement underneath them is a logged, retrievable record — the UI citation is the tip of that iceberg, not the whole thing.

Wrap-up Full Pipeline Recap
▸
Think First: across the whole pipeline — load, split, embed, retrieve, generate, display — which single step, if it silently degrades, would be hardest to notice just by reading the final answer? And what would you actually monitor to catch it early? tap to reveal
Chunking and retrieval quality are the hardest to catch from the final answer alone — because the LLM will still generate a fluent, confident-sounding response even from mediocre or subtly-wrong chunks. It never says "I'm not sure these sources are relevant." A crash in loading or embedding is loud and obvious; a slow slide in retrieval relevance is silent and shows up only as answers that are "a bit off" in ways easy to write off as one-time flukes. Real production monitoring needs to check the middle of the pipeline directly — logging retrieved-chunk relevance scores, periodic spot-audits against a known-answer test set — rather than trusting that a fluent final answer means the pipeline is healthy.
1. RAG concept: Retrieve → Augment → Generate, no model weights touched
2. RAG vs. fine-tuning: RAG wins for frequently-changing/niche factual
   grounding; fine-tuning wins for deep behavioral/stylistic adaptation
3. LangChain: framework for chaining LLM steps, tools, memory, retrieval
4. Load raw document (TextLoader) → one large document object
5. Split into chunks (RecursiveCharacterTextSplitter: size=1000,
   overlap=150) → 38 chunks, each carrying source metadata
6. Embed chunks (OpenAI embeddings, 1536-dim) → store in ChromaDB
7. Test retrieval in isolation (similarity_search) before building
   the full chain — verify relevant chunks come back for real queries
8. Assemble RetrievalQAWithSourcesChain (retriever + LLM,
   chain_type="stuff") → grounded, cited answers
9. Wrap in a Gradio UI with example questions and visible citations
