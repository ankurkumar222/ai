Retrieval-Augmented Generation with LangChain: "Ask 11 Madison Park"

Notes from a hands-on RAG project — grounding an LLM's answers in a restaurant's own scraped data, using LangChain, OpenAI embeddings, and ChromaDB, with a Gradio front end and citation support. Structured for a Senior Engineering Manager comparing this against the fine-tuning project studied separately, and against your own multi-LLM bootcamp and spirituality-site knowledge-base work.
Framing What RAG Actually Is — Retrieve, Augment, Generate
▸ 
User asks a question ("What kind of food does 11 Madison Park serve?")
        ↓
RETRIEVER searches a vector database of the restaurant's own data
        ↓
Relevant chunks are found and fetched
        ↓
AUGMENT: original question + retrieved context are combined into one prompt
        ↓
GENERATE: that combined prompt is sent to the LLM
        ↓
Answer is returned — grounded in the restaurant's actual data,
not just whatever the LLM happened to learn during pre-training

The core motivation: asking a general-purpose LLM directly gives an answer based only on its training data — which may be outdated, generic, or simply unaware of this specific restaurant. RAG lets you ground responses in your own current data without touching the model's weights at all.

Active Recall: What does each letter in RAG stand for, mapped to what actually happens? tap to reveal
R = Retrieve: search an external knowledge source (vector database) for relevant information matching the query. A = Augment: add that retrieved content to the original prompt as extra context. G = Generate: send the augmented prompt to the LLM, which produces a response grounded in the retrieved data.
Comparison RAG vs. Fine-Tuning — When to Reach for Which
▸
Fine-TuningRAG
What changesModel weights themselves are updatedNothing in the model changes — an external database is queried at request time
Best forDeep, stable domain adaptation on well-structured, high-quality dataFrequently-changing or niche factual information, without retraining
Updating knowledgeRequires retraining/re-fine-tuning (GPU time, cost, iteration)Just update the database — no model changes needed
Cost profileExpensive, time-consuming, needs GPUsComparatively cheap and fast to maintain
Failure modeCan lock the model into narrow behavior; overfitting riskOnly as good as the retrieval quality — poor indexing/chunking → poor answers
TransparencyKnowledge is baked into weights — no easy citation trailCan cite exactly which document/chunk an answer came from

Architect's Lens

This maps directly onto the LoRA/PEFT fine-tuning project studied separately — that project's big honest lesson was "fine-tuning is an expensive experiment with real failure modes (under-training, overfitting)." RAG's core appeal here is sidestepping that entire risk category: for information that changes often (a restaurant's menu, an internal policy doc, a squad's runbook), RAG is almost always the more defensible default, with fine-tuning reserved for cases needing deep behavioral/stylistic adaptation rather than factual grounding. Worth using this exact comparison table as a decision framework the next time an internal AI tool's requirements are being scoped for Optimus.

Active Recall: Why is RAG generally easier to keep up to date than a fine-tuned model? tap to reveal
Because updating a RAG system just means adding, removing, or editing documents in the vector database — no retraining is needed. A fine-tuned model's knowledge is baked into its weights, so keeping it current requires re-running the fine-tuning process on updated data, which costs GPU time and money.
Tooling LangChain 101 — Why Use a Framework At All?
▸

LangChain's value proposition: instead of a single prompt → single reply, it lets you chain multiple steps together (search → summarize → translate, as one example given) and compose reusable building blocks: prompts, memory, tools/plugins (calculators, code execution, search), agents (an LLM deciding which tool to use and when), and — the focus of this project — retrieval/RAG.

Architect's Lens

LangChain here plays the same role Next.js played in the Vercel course notes — an opinionated "application framework" layered on top of lower-level primitives (raw OpenAI API calls), bundling common patterns (chains, retrievers, memory) so you're not hand-assembling them yourself. Same build-vs-batteries-included trade-off as always: faster to start, but worth knowing what's happening underneath before treating any chain as a black box in a production setting.

Setup Loading the Source Document
▸

Data source: a single scraped text file of 11 Madison Park's website content (menus, contact info, chef bio, partnerships) — loaded with LangChain's TextLoader as one large document object with UTF-8 encoding. A required system dependency is flagged: Microsoft Visual C++ 14+ must be installed for LangChain to install/run correctly on Windows.

Active Recall: At this stage, is the document already split into retrievable pieces? tap to reveal
No — TextLoader reads the entire file as one single large document object. Splitting into smaller, retrievable chunks is a separate, later step using a text splitter.
Chunking Splitting the Document — Chunk Size and Overlap
▸

Large documents are hard for retrieval to work with directly — smaller chunks are easier to embed, store, and retrieve precisely. Uses LangChain's RecursiveCharacterTextSplitter with two key parameters:

  • chunk_size (set to 1000 characters): max characters per chunk
  • chunk_overlap (set to 150 characters): characters shared between consecutive chunks, to preserve context across a chunk boundary

Result: 38 chunks from the source document. Each chunk carries metadata pointing back to its source file — this is what later enables citations in the final answer.

Risk Flag — Chunk Boundaries Can Cut Sentences in Half

With zero overlap, a sentence or idea that happens to fall exactly on a chunk boundary gets split across two chunks, losing coherence for retrieval. The overlap parameter exists specifically to mitigate this by duplicating a bit of context at each boundary. Practice-opportunity experiments confirmed: smaller chunk_size (500) roughly doubled the chunk count (79 vs. 38); changing overlap to zero had a much smaller effect on chunk count but degraded context preservation at boundaries.

Architect's Lens

Chunk size/overlap tuning is a genuine engineering trade-off worth taking seriously, not a throwaway parameter: too large and you waste context window / retrieve noisy irrelevant text; too small and you fragment coherent ideas across chunk boundaries, hurting retrieval precision. Treat it like any other tunable system parameter (cache TTL, batch size) — pick a sensible default, then tune against actual retrieval quality on real queries, not gut feel.

Active Recall: Why does each chunk carry metadata pointing back to the source document, and what does that enable later? tap to reveal
The metadata (source file name) links each chunk back to where it came from. This is what lets the final RAG chain report citations — telling the user which document an answer was grounded in, which improves transparency and lets users verify the answer's source.
Embeddings Turning Text Into Vectors — And Storing Them in ChromaDB
▸

Embeddings represent the meaning of words/sentences/documents as dense numeric vectors — illustrated with a semantic feature-space example (gender × age × "royalty" axes placing man/woman/ boy/girl/king/queen/prince/princess at intuitive relative positions). The real embeddings used are far higher-dimensional (1,536 dimensions in this project, via OpenAI's embedding model) — far beyond human visualization, but the same underlying idea: semantically similar text ends up numerically close.

Practical demo tool: the TensorFlow Embedding Projector, used to explore nearest-neighbor words to "love" and "Italy" — visually confirming that semantically related words (France, Rome, Venice, Spain for "Italy") cluster together in the embedding space, via a PCA-based 2D/3D projection of the original high-dimensional space.

Chroma.from_documents(documents=chunks, embedding=OpenAIEmbeddings(...))
  → generates an embedding vector for each of the 38 chunks
  → stores all vectors + original text + metadata in a ChromaDB vector store

Architect's Lens

The embedding-space intuition (semantically similar concepts cluster numerically close) is worth having solid, because it's the entire mechanism retrieval relies on — a retrieval failure is almost always either a chunking problem (bad boundaries) or an embedding-similarity mismatch (the query's phrasing doesn't land near the right chunks in vector space), and diagnosing which one it is starts from this mental model.

Active Recall: What three things does ChromaDB store for each chunk, based on this project's setup? tap to reveal
The embedding vector (the numeric representation of the chunk's meaning), the original page content (human-readable text), and the metadata (including the source document it came from).
Testing Verifying Retrieval Before Building the Full Chain
▸

Before wiring retrieval into a full RAG chain, the retrieval step is tested in isolation using vector_store.similarity_search(query, k=N) — asking "what different menus are offered?" and confirming the top-k retrieved chunks actually contain menu-related content. This deliberately separates "can we find the right information?" from "can we generate a good answer from it?" — testing one variable at a time.

Follow-up tests with different questions ("Who is Daniel Humm?", "Is there a dress code?", "Tell me about the partnership with Magic Farms") and different k values (1, 2, 5) confirmed retrieval quality and showed k directly controls how many chunks come back.

Architect's Lens

Testing retrieval in isolation before adding generation on top is good debugging discipline — directly analogous to testing a database query independently before wiring it into application logic that also has to format and present the result. If a RAG system gives a bad final answer, this separation tells you immediately whether the fault is in retrieval (wrong/no chunks found) or generation (right chunks, but the LLM answered poorly) — two very different fixes.

Active Recall: Why test similarity_search in isolation before building the full RAG chain? tap to reveal
To isolate and verify the retrieval component works correctly (finds relevant chunks) before adding the generation component on top — this way, if the eventual RAG chain gives a bad answer, you already know whether retrieval or generation is the likely cause, rather than debugging both at once.
Chain Assembling the Full RAG Chain — RetrievalQAWithSourcesChain
▸ 
retriever = vector_store.as_retriever(search_kwargs={"k": 3})
llm = OpenAI(temperature=0)          # 0 = factual, minimal creativity

chain = RetrievalQAWithSourcesChain.from_chain_type(
    llm=llm,
    chain_type="stuff",              # "stuff" all retrieved text
                                      # directly into the prompt context
    retriever=retriever,
    return_source_documents=False,
    verbose=False
)

result = chain.invoke(query)
  → result["answer"]      : the generated, grounded response
  → result["sources"]     : cited source document(s)
  → result["source_documents"]  (if enabled): actual retrieved chunk text

chain_type="stuff" means all retrieved chunks are inserted directly into the prompt as-is — simplest strategy, but only works if retrieved content + question fits the model's context window. (Other chain types exist for larger retrieval sets that don't fit directly — not covered in depth here.)

temperature=0 is chosen deliberately for factual grounding — raising it to 1.3 in a later experiment produced answers with the same grounded facts but noticeably different wording, demonstrating temperature affects phrasing/creativity, not factual accuracy, when RAG is doing the grounding.

Architect's Lens

The "stuff" chain_type's context-window limitation is worth flagging explicitly as a scaling constraint: this works fine for a 3-chunk, small-restaurant knowledge base, but would break down for a much larger corpus (e.g. a full IDFC policy/compliance document set) where the top-k retrieved chunks alone could exceed context limits. Production RAG at scale typically needs either a map-reduce/refine chain strategy or much tighter chunk/k tuning — worth remembering as the natural next question if this pattern were ever proposed for an Optimus knowledge-base tool at real scale.

Active Recall: Why is temperature set to 0 here, and what does raising it to 1.3 actually change (and NOT change) about the RAG answer? tap to reveal
Temperature=0 minimizes randomness/creativity, aiming for consistent, factual answers. Raising it to 1.3 introduced noticeably different wording/phrasing in the response, but the answer remained grounded in the same retrieved source data — temperature affects HOW the answer is phrased, not WHETHER it's still grounded in the retrieved facts, since the retrieval step (which supplies the facts) is unaffected by the LLM's temperature setting.
Interface Gradio Front End — Questions, Citations, and Polish
▸

Final layer: a Gradio interface wrapping the chain — a question box, example questions users can click ("Is there a dress code?", "Do I need a reservation for the bar?", "Can I buy gift cards?"), a styled submit button ("Ask 11 Madison Park 🍽️"), and — critically — the answer displayed alongside its cited source, directly surfacing the transparency benefit RAG offers over a plain LLM call.

Architect's Lens

Citations-in-the-UI is the feature that turns a RAG demo into something a business could actually trust enough to deploy — for any regulated or customer-facing context, "here's the answer, and here's exactly which document it came from" is the difference between a plausible-sounding chatbot and an auditable one. Worth treating as a non-negotiable feature, not a nice-to-have, for any internal Optimus tool that answers questions from a document corpus (policies, runbooks, compliance docs).

Wrap-up Full Pipeline Recap
▸ 
1. RAG concept: Retrieve → Augment → Generate, no model weights touched
2. RAG vs. fine-tuning: RAG wins for frequently-changing/niche factual
   grounding; fine-tuning wins for deep behavioral/stylistic adaptation
3. LangChain: framework for chaining LLM steps, tools, memory, retrieval
4. Load raw document (TextLoader) → one large document object
5. Split into chunks (RecursiveCharacterTextSplitter: size=1000,
   overlap=150) → 38 chunks, each carrying source metadata
6. Embed chunks (OpenAI embeddings, 1536-dim) → store in ChromaDB
7. Test retrieval in isolation (similarity_search) before building
   the full chain — verify relevant chunks come back for real queries
8. Assemble RetrievalQAWithSourcesChain (retriever + LLM,
   chain_type="stuff") → grounded, cited answers
9. Wrap in a Gradio UI with example questions and visible citations
