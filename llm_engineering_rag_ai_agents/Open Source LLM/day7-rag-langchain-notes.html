Retrieval-Augmented Generation with LangChain: "Ask 11 Madison Park"

A hands-on project: make an LLM answer questions using a restaurant's own website data — not just what it learned in training. Built with LangChain, OpenAI embeddings, ChromaDB, and a Gradio front end that shows its sources.
Framing What RAG Actually Is — Retrieve, Augment, Generate
▸

Ask an LLM directly, and it only knows what it learned in training — old, generic, or nothing about this one restaurant. RAG fixes that by feeding it the restaurant's own live data at question time. No retraining needed.

Rough Sketch — RAG in one picture

 User: "What kind of food does 11 Madison Park serve?"
                    |
                    v
 R - RETRIEVE  ---------------------------------------------
     search a vector database made of the restaurant's OWN
     data --> pull out the chunks that match the question
                    |
                    v
 A - AUGMENT  ----------------------------------------------
     question  +  retrieved chunks  --->  ONE combined prompt
                    |
                    v
 G - GENERATE  ---------------------------------------------
     send that combined prompt to the LLM
                    |
                    v
 Answer -- grounded in the RESTAURANT'S real data, not just
           whatever the model happened to learn during training

 KEY POINT: model weights are never touched. Only the prompt
            changes. Update the database, answers update too.
Active Recall: What does each letter in RAG stand for, mapped to what actually happens? tap to reveal
R = Retrieve: search an external knowledge source (vector database) for relevant information matching the query. A = Augment: add that retrieved content to the original prompt as extra context. G = Generate: send the augmented prompt to the LLM, which produces a response grounded in the retrieved data.
Comparison RAG vs. Fine-Tuning — When to Reach for Which
▸
Fine-TuningRAG
What changesModel weights themselves are updatedNothing in the model changes — an external database is queried at request time
Best forDeep, stable domain adaptation on well-structured, high-quality dataFrequently-changing or niche factual information, without retraining
Updating knowledgeRequires retraining/re-fine-tuning (GPU time, cost, iteration)Just update the database — no model changes needed
Cost profileExpensive, time-consuming, needs GPUsComparatively cheap and fast to maintain
Failure modeCan lock the model into narrow behavior; overfitting riskOnly as good as the retrieval quality — poor indexing/chunking → poor answers
TransparencyKnowledge is baked into weights — no easy citation trailCan cite exactly which document/chunk an answer came from

Architect's Lens

Same lesson as the separate LoRA/fine-tuning project: fine-tuning is an expensive experiment with real failure risk. RAG sidesteps that risk for anything that changes often — a menu, a policy doc, a runbook. Keep fine-tuning for deep behavior/style change, not for facts. Use this table as a decision checklist when scoping any Optimus AI tool.

Active Recall: Why is RAG generally easier to keep up to date than a fine-tuned model? tap to reveal
Because updating a RAG system just means adding, removing, or editing documents in the vector database — no retraining is needed. A fine-tuned model's knowledge is baked into its weights, so keeping it current requires re-running the fine-tuning process on updated data, which costs GPU time and money.
Tooling LangChain 101 — Why Use a Framework At All?
▸

Plain LLM use is one prompt, one reply. LangChain lets you chain steps together and reuse common building blocks instead of hand-wiring everything yourself.

Rough Sketch

 WITHOUT a framework:            WITH LangChain:
 one prompt --> one reply        search -> summarize -> translate
 (build every piece yourself)    (chained steps, reusable pieces)

 LangChain's building blocks:
   [ prompts ]  [ memory ]  [ tools/plugins ]  [ agents ]  [ retrieval/RAG ]
                                (calc, code,    (LLM picks    <- this
                                 search)         which tool)     project

Architect's Lens

LangChain plays the same role Next.js played for the Vercel course — an opinionated framework on top of raw API calls, bundling common patterns so you don't build them by hand. Faster to start, but know what's happening underneath before treating any chain as a black box in production.

Setup Loading the Source Document
▸

Data: one scraped text file of 11 Madison Park's website (menu, contact info, chef bio, partnerships). Loaded whole with LangChain's TextLoader.

Rough Sketch

 11madisonpark.com  --(scrape)-->  one .txt file
                                          |
                                          v
                              TextLoader(file, encoding="utf-8")
                                          |
                                          v
                          ONE big document object
                          (menu + contact + chef bio + partnerships
                           all still stuck together, not split yet)

 Windows note: needs Microsoft Visual C++ 14+ installed,
               or LangChain won't install/run correctly
Active Recall: At this stage, is the document already split into retrievable pieces? tap to reveal
No — TextLoader reads the entire file as one single large document object. Splitting into smaller, retrievable chunks is a separate, later step using a text splitter.
Chunking Splitting the Document — Chunk Size and Overlap
▸

A big document is hard to search well. Cut it into small chunks first — easier to store and find precisely. Uses LangChain's RecursiveCharacterTextSplitter.

Rough Sketch

 ONE big document
        |
        v  RecursiveCharacterTextSplitter(
        |     chunk_size=1000,    <- max characters per chunk
        |     chunk_overlap=150)  <- shared chars between chunks,
        v                            keeps context across the cut
 [chunk1][chunk2][chunk3]...[chunk38]     --> 38 chunks total
   each chunk also carries METADATA -> source file name
                                        (this = later citations)

 WHY OVERLAP?  zero overlap:
   "...the chef trained    |   in Switzerland before..."
                          CUT HERE -- sentence broken, meaning lost

   150-char overlap: a bit of text repeats on both sides of the
   cut, so no idea gets sliced clean in half

 EXPERIMENT RESULTS:
   chunk_size 1000 -> 38 chunks
   chunk_size  500 -> 79 chunks   (roughly double)
   overlap = 0     -> chunk count barely changes,
                       but boundary context gets WORSE

Risk Flag — Chunk Boundaries Can Cut Sentences in Half

Zero overlap means a sentence can get sliced right at the boundary, losing meaning. Overlap exists to fix exactly that.

Architect's Lens

Chunk size/overlap is a real trade-off, not a throwaway setting. Too big = wastes context, pulls in noisy text. Too small = chops up ideas, hurts retrieval. Treat it like any tunable system parameter — pick a sane default, then tune against real query results, not gut feel.

Active Recall: Why does each chunk carry metadata pointing back to the source document, and what does that enable later? tap to reveal
The metadata (source file name) links each chunk back to where it came from. This is what lets the final RAG chain report citations — telling the user which document an answer was grounded in, which improves transparency and lets users verify the answer's source.
Embeddings Turning Text Into Vectors — And Storing Them in ChromaDB
▸

An embedding turns text into a list of numbers that captures its meaning. Similar meaning → numbers land close together.

Rough Sketch

 EASY EXAMPLE (3 imaginary axes: gender, age, "royalty"):

              royalty
                 |    king          queen
                 |      *             *
                 |         prince   princess
                 |            *      *
        ---------+------------------------- gender
                 |   boy         girl
                 |    *           *
                 |  man          woman
                 |   *             *
                age

    "king" is near "queen" and near "prince" -- because they
    are close in MEANING, not because the letters match

 REAL PROJECT: same idea, but 1,536 numbers per chunk (OpenAI
 embeddings) instead of 3 -- too many to draw, same principle

 DEMO TOOL: TensorFlow Embedding Projector
    type "Italy"  --> nearby words: France, Rome, Venice, Spain
    (2D/3D picture squashed down from 1,536 dimensions)

 STORING IT:
   Chroma.from_documents(chunks, OpenAIEmbeddings())
        |
        v
   for each of the 38 chunks, ChromaDB stores THREE things:
     1. the embedding vector (1,536 numbers -- the "meaning")
     2. the original chunk text (human-readable)
     3. the metadata (which source file it came from)

Architect's Lens

This embedding-space idea is the whole engine retrieval runs on. When retrieval fails, it's almost always one of two things: bad chunk boundaries, or the query's wording landing far from the right chunks in vector space. Diagnosing which one starts right here.

Active Recall: What three things does ChromaDB store for each chunk, based on this project's setup? tap to reveal
The embedding vector (the numeric representation of the chunk's meaning), the original page content (human-readable text), and the metadata (including the source document it came from).
Testing Verifying Retrieval Before Building the Full Chain
▸

Before building the full chain, test retrieval alone first — "can we find the right info?" is a different question from "can we write a good answer from it?" Test one thing at a time.

Rough Sketch

 vector_store.similarity_search("what menus are offered?", k=3)
                    |
                    v
       does the top-3 come back menu-related?  YES -- retrieval works

 more test questions tried:
   "Who is Daniel Humm?"
   "Is there a dress code?"
   "Tell me about the partnership with Magic Farms"

 k = how many chunks come back:
   k=1 -----> * (just the single best match)
   k=2 -----> * *
   k=5 -----> * * * * *   (more context, but more noise too)

 WHY TEST THIS SEPARATELY?
   bad final answer could mean:
     (a) retrieval found the WRONG chunks    -> fix chunking/k/query
     (b) retrieval found the RIGHT chunks,
         but LLM wrote a bad answer          -> fix the prompt/LLM
   testing retrieval alone tells you which one broke

Architect's Lens

Good debugging discipline — same as testing a database query alone before wiring it into an app that also formats and displays results. This split tells you immediately whether a bad RAG answer is a retrieval problem or a generation problem — two very different fixes.

Active Recall: Why test similarity_search in isolation before building the full RAG chain? tap to reveal
To isolate and verify the retrieval component works correctly (finds relevant chunks) before adding the generation component on top — this way, if the eventual RAG chain gives a bad answer, you already know whether retrieval or generation is the likely cause, rather than debugging both at once.
Chain Assembling the Full RAG Chain — RetrievalQAWithSourcesChain
▸ 
retriever = vector_store.as_retriever(search_kwargs={"k": 3})
llm = OpenAI(temperature=0)

chain = RetrievalQAWithSourcesChain.from_chain_type(
    llm=llm, chain_type="stuff", retriever=retriever
)

result = chain.invoke(query)

Rough Sketch

 question
    |
    v
 retriever (k=3) --> top 3 chunks
    |
    v
 chain_type="stuff"
    -----------------------------------------------
    "STUFF" = shove all 3 chunks straight into the
              prompt, as-is. Simplest strategy.
    LIMIT: only works if chunks + question fit inside
           the model's context window. Fine for 3
           chunks; would break on a huge document set
           (e.g. full IDFC policy library) -- would
           need map-reduce/refine chain instead.
    -----------------------------------------------
    |
    v
 llm = OpenAI(temperature=0)   <- 0 = factual, no creativity
    |
    v
 result["answer"]           <- the grounded answer
 result["sources"]          <- which document(s) it came from
 result["source_documents"] <- actual chunk text (if enabled)

 TEMPERATURE EXPERIMENT:
   temperature=0    -> same facts, plain/consistent wording
   temperature=1.3  -> SAME facts, different wording/style
   conclusion: temperature changes HOW it's said,
               not WHETHER it's grounded (retrieval
               supplies the facts either way)

Architect's Lens

Flag the "stuff" chain_type's context-window limit as a real scaling constraint. Fine for a 3-chunk restaurant knowledge base, but a large corpus (say, a full IDFC policy set) would blow past context limits. Production RAG at that scale needs either a map-reduce/refine chain or much tighter chunk/k tuning.

Active Recall: Why is temperature set to 0 here, and what does raising it to 1.3 actually change (and NOT change) about the RAG answer? tap to reveal
Temperature=0 minimizes randomness/creativity, aiming for consistent, factual answers. Raising it to 1.3 introduced noticeably different wording/phrasing in the response, but the answer remained grounded in the same retrieved source data — temperature affects HOW the answer is phrased, not WHETHER it's still grounded in the retrieved facts, since the retrieval step (which supplies the facts) is unaffected by the LLM's temperature setting.

Wrap-up Full Pipeline Recap
▸ 
1. RAG concept: Retrieve → Augment → Generate, no model weights touched
2. RAG vs. fine-tuning: RAG wins for frequently-changing/niche factual
   grounding; fine-tuning wins for deep behavioral/stylistic adaptation
3. LangChain: framework for chaining LLM steps, tools, memory, retrieval
4. Load raw document (TextLoader) → one large document object
5. Split into chunks (RecursiveCharacterTextSplitter: size=1000,
   overlap=150) → 38 chunks, each carrying source metadata
6. Embed chunks (OpenAI embeddings, 1536-dim) → store in ChromaDB
7. Test retrieval in isolation (similarity_search) before building
   the full chain — verify relevant chunks come back for real queries
8. Assemble RetrievalQAWithSourcesChain (retriever + LLM,
   chain_type="stuff") → grounded, cited answers
9. Wrap in a Gradio UI with example questions and visible citations
